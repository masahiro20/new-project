- **対象：** `peter/p3-pitch` の公開版 `bca7952`、`pitch/`
- **範囲：** 評価協力モードの録音の保存と削除（90日、依頼から7日以内）、外部への通信が無いこと、PWA と Service Worker のキャッシュの安全性、「創設サポーター」キー（d31）の設計要件

## 1. 要約
- 指摘は **15件**（medium 3、low 9、info 3）。**critical と high は0件**。
- **外部への通信は0件（実測）。** ソースとビルド済みの成果物の両方で、fetch・XHR・WebSocket・sendBeacon・外部の src や href・フォント・CDN・分析タグは無い。Chromium の net-log で、LP → アプリ → SW の登録 → 同意 → 判定と保存 → 共有カード → Anki → zip の書き出しまでを通し、ページと SW 由来の外部リクエストが0件であることを確かめた（それ以外の接続は Chromium 自身のサービスだけ）。ONNX と WASM の取得先もローカルの vendor だけ。
- **録音は、同意したあとにだけ端末の IndexedDB に保存される**（同意前はデータベースも作らない）。音声は判定区間だけを 16kHz の wav にしたもので、最長4秒。元のファイルとファイル名は保存しない。サーバーへの送信は無い。
- **問題は「90日・7日」の約束の担保。**
  - **端末内の録音には期限が無く、自動では消えない**のに、同意欄は「90日」と書いている。この90日は、開発者が受け取った分の話（A-1）。
  - 開発者側の「受領から90日で削除・依頼から7日以内に削除」には、**運用の手順、受領の台帳、依頼の窓口、提出物を見分ける ID が無い**（A-2）。コードでは担保できないので、手順書が要る。
- **PWA：** SW の設計（scope、キャッシュの対象、古いキャッシュの削除）は正しい。ただし `masahiro20.github.io` を他のアプリと共有しているため、同じオリジンの他のページに XSS があると、Pitch のキャッシュを書き換えて恒久的な XSS にでき、録音（IndexedDB）も読める（B-01）。根本の対処は、配信元のオリジンを分けること。
- **パッチは6本。** 全部を新しいコピーに当て、`build:demo` と `build:pwa` で作り直した結果、単体テストは **196/196**、qa-pwa は **27/27**、qa-evalmode は **45/45**、qa-demo は **19/19** で、すべて合格した。

### すぐやるべき3つ
1. **評価協力の録音を集め始める前に、0001〜0003 を当てて手順書を作る（A-1、A-2）。** 同意欄に「端末内には期限が無く、自動では消えない」と書く。書き出しに exportId を入れ、削除の依頼で伝えてもらう。受領の台帳、依頼の窓口、派生データ（評価用のマニフェスト、CSV、結果表）も同じ期限で消すことを docs に書く。プライバシーポリシーの「TO FILL」を埋める。
2. **録音を集める前、キーを売る前に、Pitch を専用のオリジンに移す（B-01）。** 当面は 0005 で恒久的なキャッシュ汚染を防げるが、同じオリジンのページから IndexedDB を読まれることは防げない。
3. **0006（CSP）と 0004（外部通信のチェックをビルドの失敗にする）を当てる。** 「録音は端末から出ない」という約束を、ブラウザとビルドの側でも担保する。

## 4. PWA の実測（Playwright と Chromium）
- 本番と同じ `/new-project/pitch/` の下に配信し、同じオリジンの別のページと、ルートの SW も用意して試した。
- **scope** は `/new-project/pitch/app/`。キャッシュは `pitch-app:<scope>:<版>` の1つで、7ファイル（版の名前は公開中の sw.js と一致）。
- **汚染の試み**（クエリ文字列付きの取得、存在しないページ、1段深いパス、`?<script>` を付けた移動）では、キャッシュは変わらなかった。404 は保存されない。
- **更新：** 1回目は古い版、2回目で新しい版。古いキャッシュは消え、他のアプリのキャッシュは残った。
- **オフライン：** 開き直し、`index.html`、`?word=`、存在しないページへの移動のどれでも、200 でアプリが出た。
- **0005 を当てた後：** 中身の違う index（CDN の古い写しの想定）、404、500 の版はどれも有効にならず、半端なキャッシュも残らなかった。他のページが Pitch のキャッシュを書き換えても、正規の版が出た。

## 5. 「創設サポーター」キーの設計要件（実装はまだ）
d31 の内容は、`peter/hq-revenue` の `peter-hq/revenue/p3-monetization.md` にあった（$19 の買い切り、30日返金、Ko-fi で販売しキーは手作業で送る、判定の無制限化などを解除、Pro の最初の1年は無料、メールアドレスを扱うのでプライバシーポリシーの更新が必要）。

1. **目的：** 守るのは、善意の支援者の特典と、気軽な共有の抑止。改変から守るもの（DRM）ではなく、開発者ツールで外せることは認める。そのうえで、秘密鍵が無ければ偽造できない、共有されたキーを次のリリースで止められる、個人情報を入れない、ずっとオフラインで使える、の4つを目標にする。
2. **署名：** Ed25519 だけ。署名の対象は `"pitch-supporter-v1\0" + payload`（Kotomark などの他の用途と区別する）。受け取ったバイト列のまま検証してから中身を読む。WebCrypto の Ed25519 を第一の経路にし（Chrome 137 以降、Firefox 129 以降、Safari 17 以降）、使えなければ小さな純 JS の検証（版を固定して vendor/ に置き、ライセンスも同梱）に切り替える。2つの経路で結果を揃えるため、正規でない署名（S ≥ L）や小さい位数の点を先に拒否し、RFC 8032 のテストベクタを両方で通す。
3. **形式とペイロード：** `PITCH1-` に Crockford base32 を続ける。正規化は前後の空白、大文字・小文字、ハイフンだけで、入力は512文字まで。ペイロードは固定長のバイナリ（`v`、`kid`、`lid`（96〜128ビットの乱数）、`plan`、`iat`（日単位））。解除する機能はアプリ側で plan から決める。**メールアドレス、名前、Ko-fi の注文番号は入れない。** lid と注文の対応表は公開しない場所に置き、保管期限を決めて消す。
4. **時刻：** 買い切りなので期限を付けず、端末の時計に頼らない。Pro の「最初の1年無料」は Pro を始める日から数える。
5. **保存：** localStorage の `pitch:supporter:v1` にキーの文字列そのものを置き、起動のたびに検証し直す（「unlocked=true」のような印は保存しない）。保存のときに persist() を要求し、消えたら購入時のメールから入れ直すよう案内する。キーをリンクで渡すときは `#key=…` を使い、読んだら URL から消す。**共有オリジンでは他のページからキーを読まれるので、販売の前に専用のオリジンに移す（B-01）。**
6. **共有と流出：** 端末に結び付けない（端末の指紋が要り、プライバシーの約束と矛盾するため）。代わりに「サポーター #A7K3」のような短い表示を出し、流出したキーは次のリリースの失効リストに入れ、正規の購入者には出し直す。
7. **失効：** 返金や流出のときは、その lid を各リリースに埋め込む失効リストに入れる（購入画面にも書く）。署名鍵が漏れたら、その kid を外して全員に出し直す。更新しない端末に効かないことは受け入れる。
8. **鍵と配置：** 秘密鍵はオフラインで作り、キーを作るツールは公開しない別のリポジトリにする。公開物の検査で PRIVATE KEY の形を禁止する。公開鍵の一覧はビルドに埋め込み、期待する値と照合する。本番には、検証を飛ばす経路（`?supporter=1` など）や公開鍵を差し替える経路を作らない。検証に失敗したら無料の機能に戻す。キーはコンソール、エラーの文、評価協力の書き出し、Anki、共有カードに出さない。評価協力の書き出しにサポーターかどうかを入れない（支援者と録音が結び付くため）。
9. **偽造のテストパターン：** 別の秘密鍵で同じ kid を名乗ったもの、ペイロードの改ざん、2つの正しいキーの署名の入れ替え、未知の kid、外した kid、署名が64バイトでないもの、S ≥ L、小さい位数の点、正規でない base32、版の接頭辞の違い、別の用途（Kotomark）の署名、大きすぎる入力・空の入力、失効した lid、localStorage に「解除済み」の印だけを書いても解除されないこと、WebCrypto の Ed25519 を無効にしても同じ結果になること。

実装ができたら、Atlas が上のパターンでレビューする。

## 7. パッチの無いものの方針
- **A-2 の手順書：** 受領の台帳（exportId、受領日、削除予定日）、依頼の窓口、削除する人、派生データとバックアップも同じ期限で消すこと、同意文の版の記録。
- **B-01：** 専用のオリジン（独自のサブドメインか、専用の組織の Pages）に移す。それまでは、同じ gh-pages の他のプロジェクトの決まりとして、`/` や `/new-project/` を scope に含む SW を置かない、caches.keys() で全部消さない、localStorage.clear() をしない。
- **A-4：** メタデータを同意欄に列挙するか、削る・丸める。meta のキーの許可リストをテストする。
- **A-5：** 一覧に「再生」を足し、README の文言を直す。
- **A-8：** QA を net-log で数え、上の3点を確かめるテストを足す。
- **A-10：** LP の文言に「本人が書き出す場合を除き」を添える。
- **B-04：** IndexedDB の版を上げるときに onversionchange で close する。
- **B-05：** 録音やキーを保存するときに persist() を要求する。
