## 新しく見つかった問題
1. **【medium】demo 構成の本番では、例の秘密値が警告だけで通る（R1-13 の修正のすき間）。** `refuseDummySecret` は、`PAYMENTS_MODE=demo` を明示していると警告を出すだけになる。docs では本番は当面 demo なので、`.dev.vars.example` の値をそのまま本番に入れると、公開されている `ACCESS_SECRET` で任意のアカウントの Cookie を偽造でき、本物のトークンが公開されている鍵で暗号化される。それでもサイトは動き続ける。**対策：** 警告で済ませるのは NODE_ENV が development/test のときか、明示のフラグ（例：`ALLOW_DUMMY_SECRETS=1`）があるときだけにし、公開の demo ではエラーにする。
2. **【low〜medium】索引から外す処理と再開の競合（R3-02）。** cron が「inactive」と判断した直後に `setStatus(active)` → `reindexAccount`（SADD）が走ると、そのあとに cron の SREM が実行され、有効なアカウントの接続が黙って監視から外れる。**対策：** SREM の前に entitlement を読み直す。または、週1回 `rebuildConnIndex` で突き合わせる。
3. **【low】demo の接続の取りこぼし（R3-02）。** その時間に確認する demo の接続は `.sort().slice(0, 2)` で選ぶので、毎回、辞書順で先頭の2件だけになり、3件目以降は cron で一度も確認されない。試用が終わった demo の接続も見つからず、`bg:democonns` が増え続ける。テストは「0件より多く、上限以下」しか見ていない。
4. **【info】R2-04 の本文ハッシュによる重複排除。** 翌月の本物の 100% 通知が、たまたま同じ本文だと捨てられる。cron が自前で取得した支出で判定するので、停止が遅れることはあっても、失われはしない。

「arm 済みの接続は毎時確認する」を採らなかった判断は**条件付きで妥当**。226件を超えると live の接続でも12時間ごとの確認になるので、そこに達する前に、live の接続だけを件数の上限付きで毎時確認にするか、Upstash を有料にするかを決めること。
