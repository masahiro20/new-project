## 5. ① 署名付きライセンスキーの設計要件（実装はまだ）
1. **アルゴリズムと鍵：** Ed25519 だけを使い、検証側は鍵の種類が `ed25519` であることを確かめる。バンドルには公開鍵の一覧（`kid` → 公開鍵、有効期間）だけを入れる。秘密鍵は KMS か HSM かオフラインのマシンに置き、発行ツールは別の非公開リポジトリにする。公開物の検査では PRIVATE KEY の形を禁止する（0008 で実装済み）。
2. **形式：** 例 `KM1.<b64url(payload)>.<b64url(sig64)>`。版の接頭辞でアルゴリズムを1つに固定し、`alg`・jwk・x5u のような、キーの側から指定させる項目は受け付けない。署名の対象は `"kotomark-license-v1\0" + payload`（別の用途の署名と区別するため）。受け取ったバイト列のまま検証し、検証してから JSON を読む。
3. **ペイロード：** `v`、`kid`、`lid`（128ビットの乱数）、`sub`（顧客）、`name`、`plan`、`features`（既知の値だけ）、`limits`、`iat`、`nbf`、`exp`（整数の秒）。必要なら `bind`（GitHub の組織など）。zod の strict で型を検証し、未知の項目と重複キーは拒否する。キー全体は 2KB まで、`exp - iat` にも上限を設ける。
4. **時刻：** 時計は利用者が変えられる前提にする。`now < iat - 許容誤差` と `now < ビルド日時`（バンドルに埋め込む）は巻き戻しとみなして拒否する。期限は購読期間に少しの猶予を足す程度にする（CI は使い捨てなので、前回見た時刻の保存には頼らない）。
5. **ローテーションと失効：** オフラインでは即時に失効できないので、期限の短いキー（例：90日、自動更新）にする。各リリースに、失効した `lid` と使えなくした `kid` の一覧を埋め込む。署名鍵が漏れたら、次のリリースでその `kid` を外し、キーを発行し直す。
6. **置き場所：** 検証は ELv2 のエンジンの中の、上限を判定する場所に置く（MIT の run.sh や CLI の引数の処理には置かない）。失敗したときは無料枠に戻し、異常終了はさせない。本番のビルドには、公開鍵を差し替える経路や検証を飛ばす経路を作らない（あると、別の公開鍵による偽造がそのまま通る）。いずれ外されることを前提に、法的な拘束と組み合わせる（ELv2 の回避禁止条項、バンドル先頭のライセンス文、レポートへの「Licensed to <name>」の表示、キーに顧客名を入れて流出元を追えるようにする）。公開リポジトリはライセンスが混在するので、ラッパーは MIT、`dist/` は ELv2 にし、release スクリプトが両方を出力して検査するようにする。
7. **キーの扱い：** GitHub Secret の環境変数で渡し、run.sh で `::add-mask::` をかける。JSON、JUnit、ログ、エラーメッセージにキーを出さない。外部への通信はしない。
8. **テストで確かめる偽造のパターン：**
   - 署名とペイロードの関係を崩すもの：別の有効なキーの署名への付け替え、プランや期限を書き換えたペイロード、未知の `kid`、正しい `kid` で別の秘密鍵が署名したもの、別の製品・用途の署名。
   - アルゴリズムの差し替え：`alg:none`、公開鍵を HMAC の鍵に使ったもの。
   - 期限と時刻：期限切れ、`nbf` が未来、`iat` が未来、時計の巻き戻し。
   - 符号化と形式：署名の長さが64バイトでないもの、正規でない base64url、重複キー（`"plan":"solo","plan":"studio"`）、大きすぎるペイロード、未知の `features`、空文字列、版の違い。
   - 失効：失効した `lid`、外した `kid`。
   - 本番のビルドで、鍵を差し替える経路が効かないこと。

実装ができたら、Atlas が上の偽造パターンでレビューする。

## 7. パッチの無いものの方針
- **B-02（high）：** 用語数の上限と「用語数 × 行数」の予算を設ける。検査を worker_threads に移して時間制限で打ち切る。利用者ごとの同時実行を1本にする。

- **B-15：** 復号できないファイルは飛ばしてログに出し、アカウント削除は続ける。
