# P5 Atlas ステージ3：新しい100件でのホールドアウト検証（2026-10-09 / Atlas）

## 結論
- チューニングに使っていない、無作為抽出の100件で測り直した。src/skill の high/critical の検出 **35件のうち、誤検知は28件（80%）、実在するが用途は正当なものが7件、攻撃型パターンは0件**だった。チューニングに使った100件での「0%」は、**この標本では再現しなかった**。
- 誤検知28件のうち26件は、**セキュリティツール5件の中にある、それ自身の検出ルール・テストベクトル・評価データ**から出ていた（scopeblind 10、AperionAI/shield 7、entroly 3、agentic-sdlc 3、wasmagent 3）。残りは、圧縮された CSS の中のゼロ幅空白と、`setup.py` という名前の CLI モジュールだけだった。
- v1.1 の誤検知対策の規則は、この100件では**一度も働かなかった**（v1 と v1.1.1 の結果は同一）。v1.1 は、チューニングに使った標本にある誤検知の形だけを捉えていた。
- **検出漏れ：** 抑制した検出、または低い重大度にした検出から40件を無作為に選んで確認したところ、**見逃しは0件**だった。ただし、この標本には攻撃型パターンが1件もないため、検出率（recall）はこのホールドアウトでは測れない。
- **「要レビュー」に格下げされた正当な用途：0/7（0%）。** 正当な7件は、どれも high/critical のまま残った（チューニング用の標本では 2/9 が格下げされていた）。
- この結果に合わせて、LP の数字はホールドアウトで測った値だけに差し替えた。精度の数字は LP にも企業向け資料にも載せていない（§5）。

## 3. ラベル付けの方法
- 判定の対象は、どちらかの版で src/skill の high/critical になった検出（35件。両版の和集合だが、両版で同一だった）。
- ラベルは**2回、互いに独立して**付けた。どちらも、スキャナーの重大度・版・抑制の有無・理由を**見ていない**。基準はステージ2 §3 と同じで、判断はコードの中身だけで行い、誰のリポジトリかは考慮していない。ラベルを付けたのは、それぞれ別に動かした AI のレビュー担当（人間ではない）。
- 2回のラベルの一致率は **34/35（Cohen の κ = 0.92）**。食い違った H013（インストールスクリプトのエラー表示が、自分のインストーラーを `curl | sh` で再実行するよう案内しているもの）は、リーダーが **fp** と裁定した。表示されるだけで実行されない文字列で、ステージ3で同じ形の案内文を扱ったのと揃えた。
- 検出漏れの確認：スキャナーが「見たが high/critical として報告しなかった」476件から、40件を同じシードで抽出した（抑制した28件、src/skill で low/medium の12件）。2回とも同じ条件で判定し、**見逃しは 0/40** だった。0/40 から言えるのは、この母集団の見逃しが概ね 7% 未満（3/n の目安）ということまでである。
- 全ラベル：`stage3-holdout-labels.json`

## 5. 何を意味するか
- MCP Registry の無作為標本では、**攻撃型パターンはめったに出ない**。high/critical として出る検出の大半は、**セキュリティツール自身が持っている攻撃サンプル**である。この分野ではセキュリティツールが多いので、ここが精度の分かれ目になる。
- v1.1 は、チューニング用の標本に合わせすぎていた（カタログの形の判定は、Cisco のデータ構造に合わせていた）。**標本の外で効く一般的な規則**が必要である。
- そのため、**LP と企業向け資料には精度の数字を載せない**。載せるのは、ホールドアウトの規模（100件、41,320ファイル、実行0、到達不能 15/115）だけにした。企業向け資料には「精度は基準に届いておらず、修正を新しい標本で検証するまで数字は出さない」と明記した。

## 6. 次の手（v1.2）。このホールドアウトはチューニングに使わない
いま見ている100件で規則を調整すると、また楽観的な数字になる。そこで、規則の案はこの結果から**種類の単位で**立て、検証は**3つ目の新しい無作為標本**で行う。

1. **データファイルの扱い：** JSON・YAML・TOML のデータの中にある TP/RF 系は、MCP マニフェストやツール定義（`tools`、`description` などの決まったキー）でなければ medium（要レビュー）にする。
2. **検出ルールやコーパスの判別：** 攻撃句が10件以上並ぶ配列や辞書、`pattern`・`regex`・`vector`・`corpus`・`expected` のような周辺のキーを手がかりに、データとして扱う。
3. **Rust の `#[cfg(test)] mod tests` と、Go の `_test.go`：** test の文脈として扱う。
4. **圧縮された CSS や JS：** OB-001（不可視文字）は、`content:` の値や、圧縮されたファイルでは low にする。
5. **CLI モジュール名の `setup.py`：** setuptools の `setup(` を呼んでいなければ、IN-002 の対象から外す。
6. 新しい無作為の100件で、同じ手順（独立した2回のラベル付け、スキャナーの判定は見せない）で測り直す。目標は、誤検知率 10% 未満、かつ陽性対照の検出漏れゼロ。
