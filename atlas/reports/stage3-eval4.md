# P5 Atlas ステージ3：4つ目の標本で v1.3 を検証（2026-10-09 / Atlas）

## 結論
- 新しい無作為の100件（eval4-100）で測った。**v1.3 の誤検知率は 87.1%（31件中27件）**で、v1.2 の 82.8%（29件中24件）より**悪くなった**。目標の 10% 未満には届いていない。
- 攻撃型パターンは **0件**（無作為の標本では3回続けて0件）。正当な用途は4件。見逃しは 0/40（v1.3 で格下げされた1件を含む）。
- 2回のラベル付けの一致は 31/32（κ = 0.87）。食い違った E024 は legit と裁定した。
- 悪くなった理由：v1.3 は「エージェントに届く場所」の中を厳しく見るようにした。そのため、**セキュリティツールが自分のツール説明文の中で攻撃の手口を解説している箇所**（3件）が high に戻った。一方で、アプリ自身のシステムプロンプトにある正当な上書き表現（1件）は medium に下がった。
- **規則を足していくやり方では収束しない**と判断した。標本を変えるたびに、誤検知の主な種類が変わる（ホールドアウトは検出ルールのデータ、検証用は Go の設定読み込みとテストのパス、今回は検出ルールの不可視文字の一覧、`.claude/settings.json` の deny 設定、説明文の中の手口解説）。

|---|---:|---:|

**v1.3 の誤検知の内訳（27件）：** 検出ルールの不可視文字の一覧と送信先の正規表現 12、`.claude/settings.json` の deny 設定（読み取り禁止のパス）5、docstring での手口の説明 4、検査 API に送るテスト文やツール説明文の中の引用 3、その他 3（入力欄の placeholder、評価用の変換関数、「〜とユーザーに言うな」の案内）。

## 4つの標本を通して分かったこと
| 標本 | 攻撃型 | 誤検知率（その時点の最新版） |
|---|---:|---:|
| チューニング用（厳選を含む） | 17 | 0%（v1.1.1） |
| ホールドアウト | 0 | 80%（v1.1.1） |
| 検証用 | 0 | 82%（v1.2） |
| eval4 | 0 | 87%（v1.3） |

1. 公式レジストリの無作為の100件には、攻撃型パターンがほぼ無い。high/critical として出るのは、主に**セキュリティツール自身が持っている攻撃サンプル**である。
2. 規則で直せるのは、その標本に出た形だけである。v1.1〜v1.3 の規則は、それぞれ次の標本ではほとんど効かなかった。
3. 一方で、**判定を見せない2回のラベル付けは、4回とも 94〜100% 一致した**（κ 0.87〜1.0）。人が読めば（今回は AI のレビュー担当が読めば）、文脈から正しく区別できている。

## 次の手
- **静的な規則に加えて、LLM による2回目の判定を入れる**（設計は `docs/llm-second-pass.md`、実装は `scanner/llm_review.py`。ただし、まだ一度も呼び出していない）。対象は src/skill の high/critical だけで、100件あたり約30件。費用は、設計時の見積もり（25件で入力約 $0.07）から、100件あたり数十セント未満の見込みである。
  - これには **API キーと利用料**が必要なので、本部・オーナーの判断を仰ぐ。
  - LLM の判定には、作者が書いた文章（攻撃者が操作できるもの）を読ませることになる。そのため、設計どおり「格下げだけを許し、抑制はしない」「`addresses_reviewer` が true なら判定を無視する」という制限を付ける。
- キーが用意されるまでの間は、製品の表示を変える。high/critical の件数を前面に出さず、「**エージェントに届く場所で見つかったもの**」と「**それ以外の場所での引用・データ（要レビュー）**」を分けて見せる（v1.3 の区分をそのまま UI に使う）。
- 精度の数字は、引き続き LP と企業向け資料に載せない。
