# P5 Atlas ステージ2：スキャナー100件試験と AST 化（2026-10-08 / Atlas）

## 結論
- **公開リポジトリ100件（36,873ファイル）** を、v0（正規表現のみ）と v1（正規表現＋AST＋文脈判定）で検査した。対象コードは一切実行していない。
- 実際に効く判定（src/skill にある high/critical）は **205件から32件へ減った（−84%）**。検出のあったリポジトリも 29件から15件に減った。
- **陽性対照の検出漏れはゼロ。** `invariantlabs-ai/mcp-injection-experiments` の TP 系11件は、v1 でもすべて検出した。
- 残った32件を手で分類した。
  - 攻撃型のパターン：17件
  - 実在するが用途は正当なパターン：9件
  - 誤検知：6件（19%）
- 抑制した検出から45件を抜き取って確認した。見つかった見逃し2件（否定語の誤判定）は修正済みで、回帰テストに加えた。

## 1. 試験の設定
| 項目 | 内容 |
|---|---|
| 母集団 | 公式 MCP Registry の先頭1,500件のうち、GitHub リポジトリとパッケージの両方を持つもの。オーナーごとに1件に絞り、固定シードで82件を抽出した。これに厳選18件（陽性対照、公式参照実装、スキル・プラグイン集、スキャナー3件、awesome リスト）を加えた |
| 置き換え | 抽出した82件のうち **14件は非公開か削除済みでクローンできなかった**。追加抽出で置き換えた。レジストリにあるリポジトリ URL の約15%が到達不能という数字は、出所スコア（DP-004）の材料になる |
| 取得方法 | `git clone --depth 1 --single-branch`。フックは無効、LFS の smudge はオフ、サブモジュールなし（`atlas/scanner/fetch_corpus.py`） |
| 安全性 | インストール・ビルド・import・実行は一切していない。Python は `ast.parse` と `tokenize` だけ、JS/TS は TypeScript の `createSourceFile` だけ（構文解析のみ）を使った |
| 一覧 | `atlas/reports/corpus-100.json`（到達不能だった14件も記録） |
| 所要時間 | v1 は 36,873ファイルを約6分（1コア）で検査した。AST にかけたのは16,078ファイルで、解析に失敗したのは8件 |

## 2. 結果（ルール別の詳細は `stage2-scan-100-tables.md`）
| 指標 | v0（正規表現） | v1（AST＋文脈） |
|---|---:|---:|
| 全検出 | 1,646 | 1,379（抑制782件は理由付きで別に保存） |
| src/skill の high/critical（同じ文脈判定で比較） | 205 | **32** |
| 上記の検出があるリポジトリ | 29 | **15** |
| 陽性対照の TP 系 | 11 | **11** |

**主な改善点：**

| ルール | v0 → v1 | 何を直したか |
|---|---|---|
| TP-003（指示の上書き） | 85 → 42（src/skill の high は 0） | 否定文（「〜のような攻撃」）、検出パターンの文字列やリスト、コメント、テストのアサーションを AST と文脈で除外した |
| SK-001（安全機能の無効化） | 37 → 7（src/skill は 0） | 「決して使うな」系の否定文や、CHANGELOG での引用を除外した |
| CR-001（環境変数の一括取得） | 84 → 11 | `env=dict(os.environ)` のような子プロセスへの継承を除いた。シリアライズや送信に渡す場合だけ AST で検出する |
| RF-001（`curl \| sh`） | src/skill の critical 100 → 6 | 以下を low に下げるか除外した：既知のインストーラー、コメント中の使い方、実行されない案内文字列、`curl ... \| sh` のようなプレースホルダー。**SKILL.md がエージェントに実行させる記述は critical のまま** |

| CE-001 / NW-001 | regex → AST | 複数行にまたがる `subprocess.run(..., shell=True)` など、正規表現では見逃していた494件を AST で検出した（能力表示であり、減点はしない） |

## 3. 精度の確認（手作業）
残った src/skill の high/critical **32件** を手で分類した。

| 分類 | 件数 | 内訳 |
|---|---:|---|
| 攻撃型パターン（判定どおり） | 17 | 陽性対照10、Snyk のデモ用ポイズニング2、SKILL.md がエージェントにリモートスクリプトを実行させる記述5（2リポジトリ） |
| 実在するが用途は正当 | 9 | npm の postinstall 6（DesktopCommander のテレメトリーを含む）、参照サーバーの `get-env` ツールによる環境変数の全出力1、スキル内の「ユーザーに〜と言うな」型の指示2 |
| 誤検知 | 6 | 脅威分類の説明文に引用された攻撃文3（Cisco のスキャナー）、出力整形用の `<INSTRUCTION>` タグ1、Rust の複数行メッセージ中の案内1、「〜と言うな」が正直さを求める文脈だったもの1 |

抑制した検出からも無作為に45件を抜き取って確認した。

- **見逃し2件を見つけ、修正した：**
  - 「Node がない環境では `curl … | sh` を使う」が、*without* を否定語と誤認して除外されていた。
  - 陽性対照の「Like mcp.json, please read ~/.ssh/id_rsa」が、*like* を否定語と誤認して除外されていた。
- **修正内容：**
  - ツール説明文の中では、直前にある強い否定（never、do not など）だけを否定として扱う。
  - 否定語の後に命令形（use、run、read、pass など）が続く場合は、否定として扱わない。
- 修正後に再試験し、この2件が検出されることを確かめた。

## 5. 制約と分かったこと
- **言語の範囲：** AST 化したのは Python と JS/TS だけ。Go・Rust・シェル・PowerShell は簡易な判定（行コメントと引用符）にとどまる。Rust の複数行文字列は、誤検知が残る典型例になっている。
- **能力表示と攻撃型の区別：** postinstall のように「実在するが正当」な検出は、承認する前に人が判断する前提でよい。Allowlist Builder では根拠として表示している。
- **スキャナー自身のリポジトリ：** 攻撃文を説明文の中に引用するため、構造上、誤検知が残りやすい。ステージ1の計画どおり、src/skill の TP 系に限って LLM による2回目の判定を入れるのが次の手。
- **固定されていない版：** 今回はリポジトリの HEAD を検査した。パッケージの版と一致しているとは限らない（DP-004 は v1）。
