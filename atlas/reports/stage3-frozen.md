## 分かったこと
1. 公式レジストリの無作為標本には、攻撃型パターンがほぼ無い。high/critical として出るのは、主にセキュリティツール自身の攻撃サンプル、検出ルール、テストデータである。
2. 規則で直せるのは、調整に使った標本に出た形だけだった。v1.1〜v1.3 の規則は、次の標本ではほとんど効かなかった。
3. 文脈を読めば区別はできる（ラベル付けがほぼ一致する）。だから次の手は、LLM による2回目の判定である（格下げだけを許し、抑制はしない。`addresses_reviewer` が true なら判定を無視する）。

## 再開するときの手順
1. API キーを用意して `ATLAS_LLM_ENABLED=1` を設定し、`llm_review.py` を有効にする。
2. 新しい無作為の100件（5つ目。既存の4標本のオーナーは除く）で、v1.3 だけの場合と、v1.3 に LLM の判定を加えた場合を比べる。ラベル付けは、これまでと同じく判定を見せずに2回行う。
3. 指標は、誤検知率、誤った警告が出るリポジトリの数（100件あたり）、陽性対照の検出率（チューニング用の標本の攻撃型17件と、フィクスチャーの18件）。
4. 精度の数字を LP と企業向け資料に載せるのは、この再測定で目標（誤検知率 10% 未満）を満たしてからにする。
