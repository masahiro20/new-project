# P5 Atlas ステージ3：3つ目の標本で v1.2 を検証（2026-10-09 / Atlas）

## 結論
- 新しい無作為の100件（validation-100）で測った。v1.2 の誤検知率は **81.8%（22件中18件）**。v1.1.1 の 82.6%（23件中19件）と比べて、**ほとんど改善していない**。目標の 10% 未満には届かなかった。
- **攻撃型パターンは0件**だった（ホールドアウトに続いて2回目）。正当な用途は4件。抑制または低い重大度にした検出から40件を抽出して確認し、**見逃しは 0/40** だった。
- v1.2 の規則が効いたのは1件だけだった（テスト用コーパスの JSON）。この標本の誤検知は、ホールドアウトとは**種類が違った**。
  - Go の `os.Environ()` を使う設定の読み込み：6件
  - `scripts/test-*.js` など、テストと判定されないパスにあるテストデータ：6件
  - 防御用のプロンプトや docstring の中で「ignore previous instructions」を引用しているもの：3件
  - 少数例のプロンプト（few-shot）の中での引用：2件
  - 正直さを求める「ユーザーに〜と言うな」：1件
- 2回のラベル付けは**完全に一致した**（A 23件、B 40件）。

## 1. 標本と方法
- 標本：`validation-100.json`。チューニング用の標本とホールドアウトのオーナー（241）をすべて除いた 8,808 オーナーから、シード 20261010 で1オーナー1件を抽出した。厳選は入れていない。到達できなかったものは 13/113。
- 検査：v1.1.1（固定したコピー）と v1.2（2aa927c）。範囲は、生きている検出のうち ctx が src/skill で重大度が high/critical のもの。
- ラベル：両版の和集合23件について、互いに独立して2回付けた（別々に動かした AI のレビュー担当。スキャナーの判定は見せていない）。判断はコードの中身だけで行い、誰のリポジトリかは考慮していない。全ラベルは `stage3-validation-labels.json`。

## 3. 3回の測定から分かったこと
| 標本 | 攻撃型 | 誤検知率（その時点の最新版） |
|---|---:|---:|
| チューニング用（厳選18件を含む） | 17 | 0%（v1.1.1。調整に使った標本） |
| ホールドアウト（無作為） | 0 | 80%（v1.1.1） |
| 検証用（無作為） | 0 | 82%（v1.2） |

- **公式レジストリの無作為標本には、攻撃型パターンがほとんど無い。** そのため「誤検知率」は、ほぼ「誤った警告の率」になる。標本ごとに誤検知の種類が変わり、1つの標本で直した規則は、次の標本では効かない。
- このままの形で誤検知率を 10% 未満にするのは難しい。**high/critical を出す条件そのもの**を変える必要がある。
- 製品として意味のある指標は、「**100件あたり、誤った high/critical の警告が出るリポジトリの数**」（今は約9〜11件）と、陽性対照の検出率の2つだと考える。

## 4. 次の手（v1.3）。方針を変える
1. **high/critical は「エージェントに届く場所」か「実行される場所」に限る。** TP 系（指示の上書き、隠蔽、タグ）を high/critical にするのは、ツールの説明文、SKILL.md、マニフェスト、モデルへ送るプロンプトの組み立て（`messages`、`system`、`prompt` に渡る文字列）にある場合だけにする。それ以外の文字列リテラルの中の引用は、medium（要レビュー）にする。
2. **CR-001（環境変数の一括取得）は、Go でも「シリアライズや送信に渡る」場合だけ high にする。** Python・JS でやっていることを揃える。`os.Environ()` を走査して接頭辞で拾う処理や、子プロセスに引き継ぐ処理は能力表示にする。
3. **テストの判定に `scripts/test-*.{js,ts,py}`、`*-test.*`、`stress-test.*` を加える。**
4. 検証は**4つ目の新しい無作為標本**で行う。ホールドアウトと検証用の標本は、これ以上チューニングに使わない。測る指標は、誤検知率に加えて「誤った警告が出るリポジトリの数（100件あたり）」と陽性対照の検出率。

LP と企業向け資料には、引き続き精度の数字を載せない。
