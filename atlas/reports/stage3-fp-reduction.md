# P5 Atlas ステージ3：誤検知率を10%未満へ（2026-10-09 / Atlas）

## 結論
- 同じ公開リポジトリ100件（ステージ2と**同じコミット**に固定）で測り直した。src/skill の high/critical に残る検出の誤検知は **6/32（18.8%）から 0/24（0%）** に下がった。
- **攻撃型パターンの検出漏れはゼロ（17/17）。** テストの陽性対照も 18/18 で、陰性対照に high/critical は出ていない。
- 減った8件は、どれも消していない。重大度を下げ（medium 7件、low 1件）、`review: true` と理由（`why`）を付けて出力に残した。判定ルールは、リポジトリ名や所有者による許可リストを使わない一般的なものだけにした。
- 「実在するが用途は正当」の9件のうち2件も、同じ規則で medium（要レビュー）になった。悪意のパターンではなく、判断材料として表示する扱いである。

## 1. 測り方
| 項目 | 内容 |
|---|---|
| 対象 | `atlas/data/index.json` に記録したコミットで100件を取得し直した（100/100、代替や失敗はなし）。フックは無効、LFS なし、サブモジュールなし、`core.symlinks=false`。インストールや実行は一切していない |
| 基準 | 変更前のスキャナー（コミット 00d6b8f）を別の場所に固定して実行した。ステージ2の数値（検出 1,379 件、src/skill の high/critical 32 件、陽性対照の TP 系 11 件）をそのまま再現した |
| 正解ラベル | `stage3-labels.json`。32件それぞれに attack / legit / fp と理由を付けた（17 / 9 / 6、ステージ2 §3 と同じ）。**スキャナーを変える前に確定**させた。判断はコードの中身だけで行い、誰のリポジトリかは考慮していない |
| 指標 | 誤検知率 ＝ fp ÷ 範囲内の検出数。範囲は抑制されていない検出のうち、文脈が src/skill で重大度が high/critical のもの。ラベルのない新しい検出は、人が確認してラベルを付ける |
| 道具 | `atlas/scanner/measure_fp.py`（標準ライブラリだけ）。消えた検出ごとに、抑制・格下げ・文脈の変化・消失のどれかを示す |

|---|---:|---:|
| 範囲内の検出 | 32 | **24** |
| 攻撃型（attack） | 17 | **17** |
| 実在するが正当（legit） | 9 | 7（2件は medium で要レビュー） |
| 誤検知（fp） | 6 | **0** |

**全検出の差分**を確認した。重大度か抑制の状態が変わったのは**ちょうど8件**だった（high→medium が7件、critical→low が1件）。重大度が上がったものも、新たに抑制されたものもない。

## 3. 何を変えたか（`atlas/scanner/README.md` の v1.1 節）
| 仕組み | 内容 | 安全のための条件 | 対象にした誤検知 |
|---|---|---|---|
| 脅威カタログの判別（AST、Python と JS/TS） | severity・threat・cwe・mitre・remediation などのキーと並ぶ `description` の値は、攻撃文を**例として引用**しているものとみなす。TP 系・SK-001 は medium（要レビュー）にする | 普通のツール一覧（name/description）は対象外。タグに隠蔽や認証情報の要求が組み合わさって critical に上がるものは、カタログの中でも critical のまま | Cisco mcp-scanner の脅威分類の説明文（3件） |
| 出力整形用のタグ | `<INSTRUCTION>` などの疑似 XML タグが、同じ文字列の中で開いて閉じ、出力の書式だけを指示している場合は medium にする | 隠す・無視する・送る、トークン、ssh、URL、ほかの TP ルール、機密パスのどれかが同じ文字列にあれば適用しない。ツールの説明文は対象外 | DesktopCommander の `prompts.ts`（1件） |
| Rust/Go の簡易な字句解析 | 複数行の文字列、`r#"…"#`、Go のバッククォート、入れ子のコメントを判別する。人向けの案内文の中にある `curl … \| sh` は low にする | 同じ文の**コード部分**に実行呼び出し（`Command::new`、`exec.Command`、`.spawn(`、`.output(` など）があれば critical のまま。v1.1.1 では、コメントや文字列の中の単語（「system」やバッククォート）は実行の文脈として数えないようにした | kin の `daemon_client.rs`（1件） |
| 正直さを求める「〜と言うな」 | 「確認するまで（unless / until）、〜とユーザーに言うな」という形は、隠蔽ではなく正直さの要求とみなし、medium にする | 隠す・送る・保存する、機密パス、ほかの TP ルールがあれば適用しない。「this」を含む場合や、about・anything で始まる場合も適用しない | dsail の `mcp_proxy.py`（1件）。同じ形の legit 2件も medium になる |
| テストの判定を広げた | `__fixtures__/`、`mocks/`、`cypress/`、`playwright/`、`*.stories.*`、`*_spec.rb`、`src/test/`、`FooTest.java` など | `demo*` と `*-docs/` は**入れていない**。入れると、本物の攻撃型2件（snyk の demoserver、fleet-memory の get-skill）が src から外れてしまうため | 今回の6件は該当なし |

**回帰テスト：** 仕組みごとに、誤検知の形をしたフィクスチャー（格下げされる）と、それに似た攻撃の形（検出が残る）を対にして加えた。例：カタログの形に `<IMPORTANT>`＋`~/.ssh` を入れた例、整形タグに「do not tell the user」を足した例、`Command::new("sh")` に渡した文字列、ドキュメントコメントの直後にある定数。スキャナーのテストは **98/98**、CLI のテストは **13/13** が通った。

## 4. 出所の証明を使った判定について（今回は見送った）
- **公開物に含まれるかどうか**（package.json の `files`、`.npmignore` など）で判定することも検討したが、入れなかった。理由は2つある。
  - TypeScript は `dist/` にビルドされるので、`files: ["dist"]` を根拠にすると、実際に動く `src/` まで「出荷されない」と誤って判断してしまう。
  - どちらも作者が自由に書ける。攻撃者が critical の検出を隠せる仕組みになる。
- 「自分はスキャナーだ」というリポジトリの自己申告も、同じ理由で使わなかった。代わりに、データの構造（カタログの形）で判定した。
- 出所の証明は、引き続き**信頼スコアの出所の項目（DP-004、npm attestation）**で扱う。誤検知の抑制には使わない。

## 5. 制約と次の手
- 正解ラベルは手作業で、件数も少ない（32件）。今回の0%は、この100件で既知の誤検知を潰した結果である。別の母集団では誤検知が出るはずなので、次は**新しい100件**（固定シード）で検証する。
- Rust の `///` ドキュメントコメントは、rmcp ではツールの説明文になりうる。v1 から引き続き、コメントとして扱っている。説明文として扱えば検出が増えるので、別の段階で対応する。
- 抑制した検出から無作為に選んだ45件（`stage3-suppressed-sample.json`）は、人による確認がまだ残っている。
