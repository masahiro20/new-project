The problem

Allowlists decide what loads. They don't review what's inside.

Enterprise allowlists are now built into the tools: Claude Code has managed-mcp.json / allowedMcpServers, and GitHub Copilot / VS Code added MCP allowlists in enterprise-managed settings. Registries don't fill the gap either: the official MCP registry (~40,700 entries in our count) verifies namespaces and leaves security checks to downstream consumers, and large directories list tens of thousands of servers with little or no review.

That leaves your team guessing — and the public record shows why that matters:

  • postmark-mcp

    An unofficial npm package that, in a later version, was reported to BCC every outgoing email to an outside address. Earlier versions looked fine; the change arrived in an update.

    Source: Koi Security report, Sept 2025 · OSV MAL-2025-47604
  • ClawHavoc / ClawHub

    341+ skills on ClawHub were reported to deliver an information-stealer (AMOS). Separately, Snyk's ToxicSkills study found critical issues in 13.4% of 3,984 skills reviewed.

    Source: Snyk ToxicSkills study and public security reporting
  • CVE-2025-6514

    Command injection in mcp-remote (CVSS 9.6), a widely used bridge to remote MCP servers.

    Source: CVE-2025-6514 record
  • Tool poisoning

    Hidden instructions in tool descriptions that steer the agent without the user seeing them.

    Source: Invariant Labs

These are summaries of third-party public reporting, not Atlas findings. Atlas findings describe detected patterns, not intent. Existing scanners help, but in our review fewer than half of their flags turned out to be real risks — and a verdict you can't inspect is hard to act on.

Early results · random holdout, internal test

What we don't do

Honest about the limits.

  • We don't run your code. Atlas never executes, installs, or imports what it checks. Sandboxed dynamic checks are roadmap.
  • Remote-only servers get metadata only. Around 58% of official-registry entries have no public source; for those we can check registry metadata, provenance and config, not code.
  • Static analysis can be evaded. Researchers (Trail of Bits) have bypassed every skill scanner tested. A determined attacker can hide from pattern matching, and some data-leak paths are only visible at runtime.
  • Not a guarantee. A verdict is evidence to support your review, not a certification that something is safe.

FAQ

Questions reviewers ask.

Do you run our code?

No. Atlas reads source, published packages and manifests statically. Nothing is installed or executed.

Does a low score mean the tool is unsafe or compromised?

No. A low score means patterns were detected that deserve a closer look — many are capabilities a tool legitimately needs (running shell commands, reading files). Read the findings, not just the number.

Can a publisher pay for a better score?

No. Scoring rules are public and identical for everyone. Paid plans buy features, never scores.

What about servers with no public source?

They receive a metadata-only verdict (provenance, registry data, launch config), clearly labelled.

Which formats can I export?

Claude Code managed-mcp.json / allowedMcpServers and GitHub Copilot / VS Code allowedMcpServers. The Allowlist Builder is a private prototype today.

What if Atlas flags something we've reviewed and accepted?

A reviewer can accept a finding; its weight drops to zero and the decision is logged.

Is there a CLI?

One is being packaged as atlas-scan, but it is not published on npm yet. We'll announce it to the waitlist first.
