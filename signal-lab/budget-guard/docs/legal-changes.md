- **起算日**：取引の日からではない。法人は、帳簿の閉鎖日・書類の作成日の属する事業年度の終了日の翌日から2か月を経過した日（法人税法施行規則59条2項）。個人は翌年3月15日の翌日（所得税法施行規則63条4項）。消費税は課税期間の末日の翌日から2か月を経過した日（消費税法施行令71条2項）。そのため「購入から7年」では足りない場合がある。本文は「期間の起算日は税法の定めによります」とした。
- **7年と10年**：欠損金の繰越控除を受ける法人は、その事業年度の帳簿書類を10年保存する。事業者（`product.config.ts` の `legal.sellerName`、未記入）が法人か個人か、青色か白色かで年数が変わる。今回は社内の決定どおり「7年」とした。
- **保存を義務づけられているのは事業者の帳簿書類**で、このアプリの KV ではない。Stripe のダッシュボードや会計ソフトに同じ記録がある場合、このアプリでも7年残す必要があるかは別の問題（下の問い①）。

**専門家への問い（購入記録）**
1. 帳簿書類の保存義務を、このアプリの KV の記録で果たす必要があるか。Stripe や会計ソフトの記録で足りるなら、アプリ側は終了後30日で消せるか。
2. 事業者が法人の場合、欠損金の繰越控除を受ける事業年度は10年になる。本文を「7年間（法令でより長い期間が必要な場合はその期間）」とすべきか。
3. 「日時・金額・プラン・請求書番号」だけの記録は、個人データに当たるか。請求書番号や Stripe の customer ID で Stripe 側の記録（メールアドレスなど）と照合できるので、容易照合性があるとして個人データの扱いになるのではないか。
4. 削除の依頼（保有個人データの利用停止・消去の請求、個人情報保護法35条）に対し、税法上の保存を理由に購入記録を残すことを、本文の書き方で十分に説明できているか。
5. 電子帳簿保存法7条の電子取引データの保存要件（検索要件など）を、このアプリの記録で満たす必要があるか。

### 2.4 購入記録の7年保存（d28）→ **実装済み（2026-10-09）**
**購入記録**（`lib/payments/purchases.ts`）：
- 本物の課金（Stripe）だけが対象。デモの購入は請求がないので記録しない。
- 1 件ずつ、別のキー `purchase:{請求書番号}` に書く。中身は次の 5 つだけで、メール・customer などの ID は入れない。
  - 日時
  - 金額（Stripe の最小通貨単位。円なら円、ドルならセント）と通貨
  - プラン
  - 請求書番号
  - 支払いか返金か

| いつ書くか | 請求書番号 | 備考 |
|---|---|---|
| サブスク：`invoice.paid`（初回と毎回の更新を 1 件ずつ） | Stripe の請求書番号（`invoice.number`）。まだない場合は請求書の ID（`in_…`） | チェックアウト完了の時点では書かない（初回の請求書で書くので、二重にならない）。**Stripe の webhook 設定に `invoice.paid` を追加する必要がある** |
| 一回払い：`checkout.session.completed` | 請求書がないので、Stripe の支払い ID（`pi_…`。なければチェックアウトの `cs_…`）で代える | — |
| 返金：`charge.refunded` | 元の支払い ID（`pi_…`） | 支払いの記録は消さず、別の記録（負の金額）を足す。キーは `purchase:refund:{charge}:{その時点の返金累計}`。部分返金が複数回あれば、記録ごとの金額はその時点までの**累計**。全額返金なら、権利を refunded にする（従来どおり） |

- 同じ請求書が 2 回届いても、`SET NX` で 1 件にする。

**削除の期限**（設定ひとつ：`PURCHASE_RETENTION = { fiscalYearEndMonth: 12, years: 7, extraMonths: 15 }`）：
- 安全側（長め）に倒した。「購入日の属する事業年度の終わり」から 7 年目の事業年度の終わりの、さらに 15 か月後の月初に消す。15 か月は、申告期限（2〜3 か月）と 1 年の余裕を見込んだもの。
- 例：12 月決算なら、2026 年中の購入は 2035-04-01 に消す。
- 決算月が 12 月でなければ、`fiscalYearEndMonth` を直す。起算日の正確な定め（税法）は専門家に確認する。
- 記録は事業年度ごとの集合（`purchases:fy:{年}`）にまとめてある。終了後30日の削除と同じ枠（cron の作業リストを作る回、6 時間に 1 回）で、期限を過ぎた年度の記録を 1 回 200 件まで消す。

**最小限の権利の記録（墓標）**：終了後30日の削除で残すものを減らした（`lib/guard/retention.ts`）。

| 項目 | 残すか | 理由 |
|---|---|---|
| ID（チェックアウトの ID）・状態 | 残す | 同じチェックアウトから権利が作り直されるのを防ぐため。権利を引くと墓標が返り、Stripe には問い合わせない |
| プラン・作成日・終了日・削除日 | 残す | 個人を識別しない。削除が規約どおりに行われたことを示すため |
| 同意の記録（版・日時・操作） | 残す | 同意の証明。個人データは含まない |
| メールアドレス・ライセンスキー | 消す（空にする） | 税務に不要 |
| Stripe の customer・subscription・payment intent の ID | **消す（今回の変更）** | 税務の記録は、上の購入記録（請求書番号つき）で足りるため |

- 墓標の期限：
  - Stripe の購入：その購入年度の購入記録と同じ日（7 年＋余裕）に、TTL で消える。
  - デモ：90 日で消える。デモの購入記録（作り直しの元になるもの）も 90 日で消えるため。

**レビューで指摘された設計上の注意**：
- 管理用の削除 API：Stripe で課金中のアカウントは、`force: true` がないと 409 で止める。削除しても、Stripe の課金は止まらないため。
- Resend への送信：10 秒のタイムアウトを付けた（`MAIL_TIMEOUT_MS`）。

**Upstash への影響**（docs/deploy-cloudflare.md §7.1）：
- 購入記録 1 件あたり 3 コマンド（`SET NX`、`SADD` ×2）。請求ごとに 1 回で、100 人が月払いでも月 300 コマンド。
- 削除の確認は 6 時間に 1 回の `SMEMBERS` 1 回（月 120 コマンド）。期限が来た年度だけ数コマンド増える。
- どちらも見積もりの 0.1% 未満。

**テスト**（`tests/purchases.test.ts`）：
- 一回払いの記録（個人を識別する情報を含まないこと、重複しないこと）
- サブスクの初回と更新（他の製品と 0 円の請求は除外、番号がないときは ID）
- 返金（部分・全額、元の記録が残ること）
- 期限の計算と、期限の前後での削除（cron 経由も）
- 墓標の項目と期限（Stripe・デモ）
- 管理用の削除 API の `force` の必須化は `tests/consent-retention.test.ts`

**残る問い**：
- 起算日の正確な定めと決算月。
- 購入記録の金額を最小通貨単位で持つ点。
- 返金の記録を累計で持つ点。
- Stripe 側の記録（Stripe のダッシュボードにある請求書そのもの）との役割分担。
