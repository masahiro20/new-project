# v1.1 総額計算（Landed Cost）設計書 — 草案

**作成：Ren（P4） / 2026-10-08 / 状態：設計のみ（未実装）→ 2026-10-09 計算エンジン・料金表の雛形・デモを試作、同日パネルの欄を実装（§11）**

## 1. 目的
出品ページの価格から、「海外の自宅に届くまでの総額の目安」を内訳つきで出す。ステージ1調査で最も多かった悩み（「5ドルの品が150〜200ドルになった」）に応えるため。

**表示は「目安」に限る。** 代行業者の手数料、送料、関税は頻繁に変わる。そのため、各数値に「いつ、どの公開情報で確認したか」を必ず添える。

## 2. 制約（v1.0 の約束を守る）
- **サーバーを持たない。** 計算はブラウザ内で行う。
- **他のページを取りに行かない。** 代行業者のサイトから料金を自動で読み取ることはしない。
- **新しい権限を最小にする。** 為替レートの扱いは §6 で選ぶ。
- 落札相場は扱わない（自動収集をしない方針）。

## 3. 計算式

```
総額 = 商品価格
     + 国内送料（出品者 → 代行倉庫）
     + 代行サービス手数料（1件あたり ＋ プラン・オプション）
     + 決済手数料（代行業者への支払い：率 ＋ 固定額）
     + 国際送料（重量・サイズ・配送方法・宛先国）
     + 梱包・保険などのオプション
     + 輸入税（関税 ＋ VAT/GST/消費税 ＋ 通関手数料）
```

- **オークションの場合、商品価格は「現在価格」ではない。** 利用者が入力した「上限入札額」を使う。入力がなければ現在価格を使い、「現在価格での試算」と明示する。
- **国内送料は自動で決めない。** 「送料込み」が読み取れれば ¥0、読み取れなければ利用者が選ぶ（目安の帯：¥0／〜¥1,000／〜¥2,000／手入力）。
- **輸入税は関税の課税価格に何を含めるかが国で違う。** 商品価格のみか、送料・保険込みか（CIF か FOB か）を、国ごとの規則として表に持つ。

## 4. データ設計：更新しやすくする

変わりやすい数字は**コードから完全に切り離し**、JSON で持つ。辞書（glossary.json）と同じ運用にする。

```
data/rates/
  proxies.json        代行業者の手数料プラン
  shipping.json       国際配送方法 × 重量帯 × 地域
  destinations.json   宛先国の輸入税ルール
  meta.json           全体の版番号、最終確認日
```

### 4.1 共通ルール（すべての数値）
各数値に次の情報を付ける。

```json
{
  "value": 500,
  "currency": "JPY",
  "effective_from": "2026-04-01",
  "checked_at": "2026-10-08",
  "source": "代行業者の公式料金ページ（URLを記録）",
  "checked_by": "人の名前またはイニシャル"
}
```

- `checked_at` から **45日**を過ぎた数値は、パネルで「古い可能性」と表示する。
- **90日**を過ぎた数値は計算に使わず、利用者が入力した値だけで計算する。
- 料金の改定日がわかっている場合は `effective_from` を付けた新しい行を足す。古い行は消さず、日付で切り替える。予告された値上げ（例：Buyee の¥500 への改定）も事前に登録できる。

### 4.2 proxies.json（例）
```json
{
  "id": "proxy_a",
  "display_name": "（業者名。表示は事実の記載に限る）",
  "plans": [
    { "id": "standard", "service_fee": {"value": 500, "currency": "JPY"}, "per": "item",
      "payment_fee": {"rate": 0.035, "fixed": 0}, "notes": "…", "checked_at": "…", "source": "…" }
  ],
  "options": [ { "id": "insurance", "kind": "rate", "rate": 0.02, "min": 200 } ]
}
```
手数料の表し方は、定額、率、率＋最低額、段階制のどれかで書く。計算エンジンはこの4種類の部品だけを解釈する。そのため、業者が増えてもコードを変えずに済む。

### 4.3 shipping.json
配送方法ごとに、重量帯と地域ごとの料金表を持つ。カメラ・時計の典型的な重量は、ジャンル別の初期値として持つ。
- レンズ：0.5kg
- 一眼レフのボディ：1.0kg
- 腕時計（箱付き）：0.5kg

利用者はいつでも上書きできる。容積重量（縦×横×高さ÷係数）は係数を表に持つ。

### 4.4 destinations.json
```json
{
  "country": "US",
  "duty_basis": "FOB",
  "de_minimis": {"value": 0, "currency": "USD", "note": "2025年8月に少額免税を廃止（要再確認）"},
  "categories": {
    "camera": { "duty_rate": null, "note": "要確認：HSコード 9006 系" },
    "lens":   { "duty_rate": null, "note": "要確認：HSコード 9002 系" },
    "watch":  { "duty_rate": null, "note": "要確認：HSコード 9101/9102 系。時計は個数・素材で課税方式が異なる国あり" }
  },
  "extra_tariff": { "rate": null, "note": "要確認：日本原産品への追加関税" },
  "sales_tax_on_import": null,
  "broker_fee": { "value": null, "note": "配送業者により異なる" }
}
```
- **税率は今は入れない（null）。** 実装の前に、各国の公的資料で人が確認して埋める。null の項目は計算に含めず、内訳に「未確定」と表示する。
- **最初に対応する宛先は5か国。** 米国、英国、ドイツ（EU 代表）、オーストラリア、カナダ。ステージ1で証拠が出た国が中心。
  - 英国・EEA からはヤフオクを直接利用できない。ただし代行経由の購入はあるため、宛先には含める。

## 5. 計算エンジン
- `src/landed-cost.js` は純粋関数とする：`(入力, 料金表, 今日の日付) → { 合計, 内訳[], 警告[] }`。
- 料金は「日付で有効な行を選ぶ」→「部品（定額・率・最低額・段階）を評価する」の2段階で計算する。
- 端数処理は手数料ごとに表で指定する（切り上げ・切り捨て・四捨五入）。
- **合計は幅で出す。** 例：$412〜$468。国内送料や重量が不確かだと、幅が広がる。
- テストは料金表のフィクスチャ（架空の業者・架空の税率）で行う。本番の料金表はテストに使わない。

## 6. 為替レート（判断が必要）
| 案 | 内容 | 権限・通信 | おすすめ |
|---|---|---|---|
| A | 利用者が自分でレートを入力する（初期値は同梱の参考値。日付付き） | 増えない | **v1.1 はこれ** |
| B | 公的な為替データを1日1回取得する | 取得先の host_permission が増え、外部通信が発生する | オーナー承認後に検討 |
| C | 拡張の更新時に参考レートを同梱する | 増えない | A と併用 |

v1.0 の「外部通信ゼロ」を保つため、v1.1 は **A＋C** で出すことを提案する。

## 7. 料金表を更新する運用

   - 人が公式ページを読んで書き写す。自動で取りに行くことはしない。
2. `npm test` で検査する：スキーマ、日付、45日・90日の期限、null 項目の扱い。
3. 拡張の版を上げて配布する。

料金表だけを差し替える Pro 向けの配信は v1.2 以降に検討する。署名付きの静的ファイルを使う案だが、サーバーと権限が増えるため、オーナー判断が必要。

## 8. 画面
パネルに「Estimated total」の欄を追加する。

- 代行業者・プランの選択
- 配送方法の選択

### 11.2 仮のもの・やっていないもの
- 料金・税率・少額免税の基準額・課税価格の方式・為替の参考レート：すべて null（要確認）。
- 代行業者：`proxy_example` の1件だけ。実在の業者名は入れていない。

- 価格の読み取り：`sites.js` はまだ価格を読まない。上限入札額（または価格）は利用者が入力する。
- 重量の不確かさ：今は点の推定（初期値を使ったときは警告を出す）。重量の幅を出すかは未定。
- 保険の扱い：CIF に含める保険は、代行業者のオプションで `counts_as: "insurance"` を付けたものだけ。

## 12. 料金表の確認記録（2026-10-09）

**担当：P4 リサーチ（Claude） / 確認日：2026-10-09 / `meta.status` を `placeholder` から `partial` に変更（data_version `0.1.0-partial`）**

本部の方針に従って記入した。値は**公式の一次情報だけ**から取り、各行に `checked_at`（確認日 2026-10-09）、`source`（公式ページの URL）、`effective_from` を付けた。確認できなかった項目は null のままにして、note に「要確認」と理由を書いた。アカウント作成、ログイン、フォーム送信はしていない。robots.txt を確認してから読んだ（EU TARIC は robots.txt で Disallow のため使わず、EU 公式の Access2Markets を使った）。§11.2 の「すべて null」は、この節の範囲で置き換わる。

- **施行日の扱い：** 出典に施行日の記載がない値は、`effective_from` に確認日（2026-10-09）を入れた。その行には `effective_from_basis` で理由を書いた。施行日が出典にある値（例：英国 VAT 2011-01-04、米国の301条措置 2026-07-24）は、その日を入れた。
- **関税率は MFN（一般税率）を使う。** 日本の特恵税率（EU・日本 EPA、日英 EPA、CPTPP など）は原産地の申告が必要なため、note に書くだけにした。米国だけは日本原産品への追加関税を合算している。
- `scripts/check-rates.mjs` に `partial` を追加した。`placeholder` は値を1つも許さない。`partial` と `verified` は値を許すが、値のある行には `checked_at`・`source`・`effective_from` が必要（従来どおり）。さらに、data/rates では `source` が https の URL であること、null の行の note に「要確認」があること、`meta.last_reviewed` があることを求める。

### 12.3 計算エンジンへの申し送り（コードは変えていない）

1. **デジタルカメラは HS 8525.89 で、9006 とは税率が違う国がある。** EU は 8525 89 00 が 0%、9006 は 4.2%。今のエンジンは `digital_camera` を `camera` にまとめているため、ドイツのデジタルカメラの関税を 4.2% で多く見積もる。米国・英国は同じ率なので影響はない。豪州・カナダの 8525.89 は未確認。区分を分けるかは判断が必要。
2. **豪州の GST の課税標準には国際送料・保険が入る**（関税は FOB）。エンジンは GST を「関税評価額＋関税」にかけるので、1,000 AUD を超えると GST を送料×10% だけ少なく見積もる。
3. **EU の150ユーロ以下の貨物には、従価の関税ではなく1品目 €3 の定額関税がかかる**（2026-07-01〜2028-07-01、通信販売の場合）。エンジンは従価で計算する。ほかに、1品目 €2 の Union handling fee が 2026-11-01 から見込み（委任規則は審査中のため入れていない）。
4. **英国の135ポンド以下では、VAT は販売者が販売時に請求する**ことになっている。代行経由のとき誰が請求するかは確認していない。エンジンは VAT を加算する（少額免除は関税だけに適用）。
5. **カナダの輸入税は連邦 GST 5% だけ。** HST の州（13%など）や PST の州では、実際はもっと高い。パネルの表示名を「Import GST (5% federal; HST provinces pay more)」にした。
6. **複合税・従量税（時計）を表す部品がない。** 米国・英国・ドイツの時計の関税は、部品が増えるまで null のまま。

## 13. エンジンの改善（2026-10-09）

**担当：Ren（P4） / §12.3 の申し送りに対応。国名はコードに書かず、汎用の部品・規則を料金表のスキーマに足して、各国の規則はデータで表した。値は §12 に記録されたものだけを使い、記録がない値は null（要確認）のまま。**

### 13.1 足した部品と規則
| 対象 | 内容 |
|---|---|
| 部品 `per_unit` | 1個あたりの定額 × 数量。通貨が宛先と違えば換算する（`fixed` と同じ扱い） |
| 部品 `rate_with_min_max` | 率を最低額・最高額ではさむ。`per: "unit"` なら最低額・最高額に数量をかける（`"line"` ならかけない）。通貨は宛先と同じであること |
| 数量 `input.quantity` | 省略時は1。1以上の整数でなければ警告を出して1にする。パネルに入力欄は出さない（1件の出品＝1個） |
| 行の終了日 `effective_until` | その日から行を使わない（その日を含まない）。`effective_from` より後の日付であること |
| 輸入税の課税標準 `tax_base` | 宛先ごとの日付つきの値。`goods`（商品価格）、`international_shipping`、`insurance`、`duty`（関税＋追加関税）、`customs_value`（`duty_basis` の結果）から選んで並べる。`duty_basis`（関税の課税価格）とは別に持つ。null（未確認）なら「商品価格＋関税」（下限）〜「商品価格＋国際送料＋保険＋関税」（上限）の幅で出し、警告 `tax_base_unknown` を出す。`tax_base` がない宛先は従来の `import_tax.base` を使う |
| 関税の区分をサブジャンルで持つ | `duty` に `digital_camera`・`film_camera` を任意で置ける。あればそれを使い、なければ `camera` に戻る。置いたのに値が null なら、`camera` の率を流用せず「未確定」にする |
| 関税の規則 `duty_rules` | 条件つきで関税の行を置き換える規則の一覧（`replaces: "duty"`、`categories` で区分を絞れる）。行に `applies_when: { max_value, currency, of }` を付けると、額が `max_value` **以下**のとき適用（境界を含む）。`of` は判定に使う額（`goods`＝商品価格、`customs_value`＝課税価格、null＝未確認で両方で判定）。どちらとも言えない範囲は、規則と通常の関税の幅で出し、警告 `duty_rule_partly` を出す。少額免税で0になる場合は規則より免税が先。利用者が関税の額を入れた場合はそれが優先 |
| 州・地域の税 `subdivisions` | 宛先に州などの一覧と、それぞれの税（率）を持つ。利用者が選んだときだけ「州の売上税」の行を足す（課税標準は輸入税と同じ、少額免税も輸入税と同じ）。選んでいなければ警告 `subdivision_not_chosen`。パネルの選択欄は、一覧がある宛先のときだけ出す |
| 注意書き `notices` | 宛先に置く注意（`when: { carriers, methods }` で配送業者・配送方法を絞る）と、配送方法に置く注意（`when: { destinations }`）。英語の文と、出典・確認日を持つ。結果の `notices[]` と、警告（code `notice`）に出す。パネルでは警告欄の先頭に出す。配送方法には `carrier`（例 `japan_post`）を足した |

`scripts/check-rates.mjs` も同じ規則で検査する：新しい部品の項目（通貨、最低額≦最高額、すべて null かすべて値か、`per`）、関税の区分の名前、関税の行の種類（rate／per_unit／rate_with_min_max）、規則の行の種類（fixed／per_unit／rate／rate_with_min_max）、`applies_when` の形（null の部分があれば note に要確認）、`effective_until`、`tax_base` の部品（`customs_value` と `goods` などの重複は不可）、州の id と英語の表示名、注意書きの英語・出典・確認日。data/rates では `import_tax` のある宛先に `tax_base` を必須にした（未確認なら null＋要確認）。
