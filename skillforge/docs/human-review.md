# 人による精度の確認（ホールドアウト第2回の再判定キット）

本部バックログ 3「人による精度の確認」のための手順です。

いま外に出している未調整の精度は1つだけです（`eval/heldout-2/`：警告・エラー 297件中 287件、96.6%、95% 区間 93.9〜98.2%）。この判定は **AI の評価者1名** が付けたもので、人はまだ確認していません。このキットは、その中から 100件を人に **ブラインドで**（AI の判定を見せずに）判定し直してもらい、数字を確かめるか直すためのものです。

- シートの生成：`scripts/human-review.mjs`（`npm run human-review`）
- 集計：`scripts/human-review-score.mjs`（`npm run human-review:score`）
- 共通の計算：`scripts/human-review-lib.mjs`（テストは `test/human-review.test.ts`）

## 1. 誰に頼むか

- **日本語と英語の両方が読める人**。ローカライズ（翻訳・LQA・ゲームやアプリの UI 翻訳）の経験があれば最もよい。
- 候補：オーナー本人、有償で頼むバイリンガルの確認者、パイロット先の担当者（了解を得た場合のみ）。
- **Kotomark の開発に関わっていない人** が望ましい。オーナーが確認する場合も数に入れてよいが、集計と LP の文では「自社の確認者」と書き分けます。
- 1名でも意味はありますが、**2名** いると確認者どうしの一致率（κ）も出せて、判定の揺れが分かります。

## 2. かかる時間

- 100件で **60〜90分** が目安（1件 30〜60秒）。未翻訳の指摘はすぐ判定できます。カタカナ表記の揺れ・タグの指摘は少し時間がかかります。
- 途中でやめても、同じブラウザで開き直せば続きから再開できます（ブラウザ内に自動保存）。

## 3. シートを作る（依頼する側）

```bash
npm run human-review
# → out/human-review/review.html（確認者に渡す）と out/human-review/key.json（手元に残す）
```

やっていること：

1. `eval/heldout-2/<プロジェクト>/source.md` から、リポジトリ・固定したコミット・ダウンロード先・sha256・check の実行方法を読み取ります。`labels.csv` から、指摘の番号（F####）・ファイル:行・文字列 ID のハッシュ・ルール・重大度を読み取ります（AI の判定はシートに入れません）。
2. 固定したコミットの元ファイルを、**リポジトリの外** のキャッシュ（既定 `~/.kotomark/review-cache/`、`--cache` で変更）に取得し、sha256 を確かめます。
3. **評価に使ったコミットのエンジン**（`eval/heldout-2/README.md` に記録された `3edc6a01…`）を `git archive` でキャッシュに取り出し、評価と同じ設定（`--no-glossary`、ルールあり）で実行し直します。同じファイル・同じ設定なので指摘は評価時と同じ順に出ます。ラベルの F#### がどの指摘かは、番号で引いたうえで「ファイル:行・ルール・重大度・ID ハッシュ」がすべて一致することを確かめています（2026-10-09 の実行では 326件すべて一致。元の実行結果とも全件同じでした）。
   - `labels.csv` だけではメッセージ・原文・訳文が無いため、エンジンを実行し直してそれらを得ています。原文・訳文は、指摘の「ファイル + 行 + ID」で表の行を引いて取ります（`msgctxt` が同じ .po の項目で別の本文が出る、以前のラベル表の問題は起きません）。
   - **今のエンジンを使わない理由**：評価の後で FP の原因を直したため（`eval/heldout-2/fixes.md`）、今のエンジンでは AI が FP とした11件が出なくなっています。今のエンジンで作ると、その11件だけメッセージが無いといった差から判定が推測できてしまいます。
   - 予備として `--engine current`（今の `src/`）もあります。その場合は「ファイル:行 + ルール（+ ID ハッシュ）」で照合し、照合できない項目が1件でもあるルールは、そのルールの全項目でエンジンのメッセージを表示しません（メッセージの有無から判定が漏れないように）。
4. 抜き取り（既定 100件、`--size`、`--seed`。既定のシードは `20261009`）：
   - 未翻訳以外の警告・エラー（全24件）は **すべて** 入れます（AI の数字がいちばん弱いところなので）。
   - 残り 76件を `untranslated.*` からプロジェクトごとのラベル件数に比例して無作為に抜きます。
   - info は既定では入れません（`--include-info` で入れる）。
   - 抜き取りは AI の判定を一切見ません。並び順もシャッフルします。
   - **結果を見てからシードを変えて作り直さない** でください（都合のよい抜き取りを選んだことになります）。
5. 出力：
   - `out/human-review/review.html`：1ファイルで完結（外部の読み込み無し、オフラインで動く）。日本語／英語の切り替え、判定ボタン（正しい指摘／誤検知／判断できない）、コメント、ブラウザ内の自動保存（localStorage）、CSV のコピー・保存。項目の ID は H001〜H100 の通し番号で、F#### や AI の判定・メモは入りません。
   - `out/human-review/key.json`：H### と元の指摘（プロジェクト・F####・ファイル:行・ルール）の対応。集計に使います。**確認者には渡しません**（判定は入っていませんが、`labels.csv` と突き合わせると AI の判定が分かるため）。

主なオプション：`--eval <dir>`（別の評価セット）、`--cache <dir>`、`--out <dir>`、`--size 100`、`--seed <n>`、`--include-info`、`--engine pinned|current`、`--engine-commit <sha>`、`--offline`（取得済みのキャッシュだけで作る）。

### 本文の扱い（ライセンス）

シートには各プロジェクトの翻訳ファイルの本文（GPL-2.0、Apache-2.0、AGPL/GPL-3.0、CC BY-SA 3.0、MIT）が入ります。ローカルで確認のために表示するのは問題ありませんが、

- `out/` はコミットしません（`.gitignore` 済み）。HTML をウェブに公開したり、不特定の人に配ったりしません。
- 確認者に渡すのは HTML ファイル1つだけ（メール添付・共有フォルダなど、相手を限定した方法で）。
- シートの末尾に、プロジェクトごとの出典・コミット・ライセンスを表示しています。

## 4. 確認者に渡すもの・渡さないもの

| 渡す | 渡さない |
|---|---|
| `review.html`、この文書の「5. 判定の基準」 | `key.json`、`eval/heldout-2/` の `labels.csv`・`README.md`・`summary.json`・`fixes.md`、AI の精度の数字、リポジトリ |

依頼の文面には「96.6% を確かめたい」と書かず、「ツールの指摘が正しいかを判定してほしい」とだけ書きます（期待値を与えないため）。

## 5. 判定の基準（確認者向け。シートの冒頭にも同じ内容を表示）

- **正しい指摘**：指摘された行に、指摘どおりの問題が実際にあり、ローカライズ QA の担当者として直したい（直すよう報告したい）もの。
- **誤検知**：指摘の内容が事実と違うもの、または事実としては正しいが直す必要がまったく無いもの（例：原文が数字・日付・記号・変数だけで、訳す内容が無い）。
- **判断できない**：情報が足りない、または担当者によって判断が分かれるもの（例：固有名詞を英語のまま残すのが意図的かもしれない）。理由をコメントに書く。

この基準は AI の評価者が使った基準（`eval/heldout-2/README.md` の「方法」）と同じです。同じ基準でないと、人と AI の数字を比べられません。

確認者の手順：

1. `review.html` をブラウザ（Chrome・Edge・Firefox・Safari）で開く。ネット接続は不要。
2. 右上に確認者 ID（名前か記号）を入れる。
3. 1件ずつ判定する（カードの中で 1・2・3 キーでも可）。迷ったらコメント。
4. 終わったら「CSV をコピー」→ メモ帳などに貼り付けて `<名前>.csv` で保存（または「CSV を保存」でダウンロード）し、依頼者に送る。

CSV の列：`reviewer_id,item_id,verdict,comment,sheet_id`（`verdict` は `correct` / `false_positive` / `cant_tell`）。

## 6. 回答を受け取ったら（依頼する側）

- `reviews/<名前>.csv` に置きます（`reviews/` は `.gitignore` 済み）。またはリポジトリの外の、本人だけが見られる場所に置きます。
- CSV に本文は入りませんが、コメントに本文が引用されていることがあります。CSV そのものはコミットしません。

## 7. 集計

```bash
npm run human-review:score -- reviews/alice.csv reviews/bob.csv
# key.json の場所が違うとき：--key <path>、評価セットの場所が違うとき：--eval <dir>
```

Markdown の報告が出ます。

- **確認者ごと**：回答数、正しい／誤検知／判断できない、そのままの精度（Wilson 95% 区間）、AI のラベルとの一致率、Cohen の κ（3分類、および両者が「正しい／誤検知」を付けた項目だけの2分類）、確認者 × AI の表、食い違った項目の一覧（コメント付き）。
- **確認者どうし**（2名以上）：組ごとの一致率と κ。
- **補正した精度の推定**：シートは未翻訳以外のルールを全数入れているので、そのままの精度は元の母集団の精度ではありません。ルールごとの精度を母集団でのルールの割合で重み付けして戻します（層別の推定。区間は層別の分散から求めた有効標本数による Wilson 法）。母集団は2つ：
  - A「AI ラベルの抽出」：`labels.csv` の `warning_error` 303件（LP の「297件中 287件」の母集団）。**LP の数字と比べるのはこちら。**
  - B「全指摘」：6プロジェクトの警告・エラー全件（`summary.json`）。
  - それぞれ「判断できない」を除いた値と、誤検知に数えた値。2名以上なら多数決（同数は「判断できない」）の値も。
  - 参考として、**同じ100件に AI のラベルで同じ計算をした値** も出ます。抜き取りの偶然で AI の値も 96.6% からずれるので、人と AI の差はこの行と比べるのが公平です。

## 8. LP・声かけ文の数字への反映

**人の確認が1名分もそろうまでは、何も変えません。** 今の文言（「自社のAI評価者による判定」）のままにし、「人が確認した」「人手で確認」とは書きません。

1名以上そろったら、集計の報告（母集団 A、「判断できない」を除いた値）で決めます。

| 結果 | 文言 |
|---|---|
| 人の補正後の推定の 95% 区間が 96.6% を含み、かつ AI との κ（2分類）が 0.6 以上 | 数字は「297件中 287件（約97%）」のまま。注記を「自社のAI評価者による判定。うち100件を確認者 N名が AI の判定を見ずに判定し直し、一致率 X%」に変える。 |
| 区間が 96.6% を含まない、または κ が 0.6 未満 | 人の値に置き換える：「…警告・エラーから無作為に抜き出した100件を確認者 N名が判定し、補正後の推定は約 Y%（95% 区間 a〜b%）」。AI の数字は使わない。 |

共通の規則：

- **AI と人の判定を合算しない**（「AI 297件 + 人 100件」のような足し算はしない）。
- 確認者の人数と属性を必ず書く（例：「外部のバイリンガル確認者2名（ローカライズ経験あり）」「自社の確認者1名」）。パイロット先の名前は、本人の許可なしに出さない。
- 「約97%」だけを抜き出さず、件数・条件（調整に使っていないオープンソース6本、主に UI 文字列、警告・エラー、指摘の大半は未翻訳の検出）を添える。「ゲーム台本で」とは書かない（`docs/outreach-drafts.md` の規則どおり）。
- 未翻訳以外の24件は件数が少ないので、人の判定で数字を出すときも「24件中 N件」と件数で書く。
- 結果はまず `docs/real-world-eval.md` と `eval/heldout-2/README.md` に記録し（確認者は ID で、個人名は書かない）、LP・声かけ文の変更は本部の承認を得てから行う。
- 補足：`eval/heldout-2/README.md` の「LP に載せてよい一文」は「人手で確認したところ」と書いているが、判定は AI 評価者なので、人の確認がそろうまでこの一文は使わない（`docs/outreach-drafts.md` の文言を使う）。

## 9. 費用について（決めるのはオーナー）

- 有償で頼む場合の目安：**確認者2名 × 1.5時間**（説明を読む時間を含む）。費用は相場・依頼先の手数料によるので、ここでは決めません。例として時給 3,000〜5,000円と仮定すると、2名で 9,000〜15,000円程度（仮定の計算で、相場は確認していません）。
- **依頼・支払い・アカウント作成は、このチーム（エージェント）からは行いません。** 依頼先を選ぶ、連絡する、支払うのはオーナーの判断です。
- 費用をかけない選択肢：オーナー本人が1名分を確認する（「自社の確認者」として扱う）、パイロット先に了解を得て頼む。

## 10. 限界

- 100件中 76件が未翻訳の指摘で、ここでの精度は実質「空の訳文を見つける精度」です（元の評価と同じ限界）。
- 人の判定も主観を含みます（とくに「訳す内容の無い原文の空欄」「船名などの固有名詞」）。2名以上で κ を見るのはそのためです。
- 再現率（見逃し）はこのキットでは測りません。
- シートは評価時のエンジン（`3edc6a01`）の指摘です。今のエンジンの精度を測るものではありません（今のエンジンは、このデータで調整済み）。
