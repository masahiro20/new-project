# ライセンスキー（オフライン検証）

本部決定 d29 で決めた「有料機能はオフラインで検証する署名付きライセンスキーで解除する」の実装メモです。
ライセンスの種類や無料・有料の線引きは [license-options.md](license-options.md)、[decisions.md](decisions.md)（d29）、
[licenses/KOTOMARK-USAGE-TERMS.md](../licenses/KOTOMARK-USAGE-TERMS.md)（下書き）を見てください。
設計は Atlas のセキュリティレビュー §5 の要件に合わせています（対応状況は [security-review-response.md](security-review-response.md)）。

> **いまはプレビュー期間です。** `src/cli/license.ts` の `PREVIEW = true` により、キーがなくても全機能が使え、
> CLI はキーについて何も表示しません。キーを渡した場合だけ検証し、期限切れ・不正なキーは警告を1行出して**そのまま続行**します。
> まだ1本も発行していません（形式を `KOTOMARK-1.` から `KM1.` に変えたのはそのため。旧形式は受け付けません）。

## 仕組み

- **外部への通信は一切ありません。** キーはバンドルに埋め込んだ ed25519 の**公開鍵**で検証します（Node の `crypto.verify`）。
  台本を外へ出さないデータ方針と同じく、ライセンス確認でも利用者の環境から何も送りません。
- 検証コードは `src/cli/license.ts`（Node 専用）、信頼の起点（公開鍵・失効リスト・リリース日）は `src/cli/license-pubkey.ts` にあります。
  ブラウザ版デモが使う `src/core` には入れていません。
- 形式：

  ```
  KM1.<base64url(ペイロードの JSON のバイト列)>.<base64url(ed25519 署名 64 バイト)>
  ```

  - **接頭辞 `KM1.` がアルゴリズムを1つに固定します。** KM1 = ed25519、署名の対象は `"kotomark-license-v1\0"` ＋ ペイロードのバイト列（**ドメイン分離**：
    別の製品・用途のために作った署名はここでは通りません）。キーの側からアルゴリズムや鍵を指定する項目（`alg`・`jwk`・`x5u` など）はありません（未知の項目として拒否）。
  - キー全体は **2,048 文字まで**。base64url は正規の綴りだけ（パディングや余分なビットは拒否）。署名は 64 バイトちょうど。
- **検証の順序：** ① 長さ・形式 → ② 受け取ったバイト列のまま署名を検証（埋め込みの公開鍵を順に試す。無効にした `kid` と ed25519 以外の鍵は使わない）
  → ③ 検証できてから初めて UTF-8 として読み、JSON を解析 → ④ 重複キーを拒否し、zod の strict スキーマで検証（未知の項目・未知の `features`・小数の秒は拒否）
  → ⑤ `kid` が署名した鍵と一致するか、`lid` が失効していないか、署名鍵の有効期間内に発行されたか、`iat ≤ nbf < exp`、`exp − iat ≤ 400日`
  → ⑥ 時刻（下記）。
- ペイロード：

  | キー | 内容 |
  |---|---|
  | `v` | 形式のバージョン（1） |
  | `kid` | 署名鍵の ID。`k-` ＋ 公開鍵（SPKI DER）の SHA-256 の先頭12桁 |
  | `lid` | ライセンス ID。**128ビットの乱数**（base64url 22文字）。失効リストと台帳で使う |
  | `sub` | 顧客 ID（台帳の ID。英数字と `_.:@-`、64文字まで） |
  | `name` | 契約者名。レポートに「Licensed to 〈name〉」と表示（100文字まで、制御文字なし） |
  | `plan` | `studio` |
  | `features` | 既知の値だけ（今は `large-runs`） |
  | `limits` | `{ "seats": 席数 }` |
  | `iat` / `nbf` / `exp` | 発行・有効開始・有効期限（Unix 秒、整数） |

- **時刻：** 利用者の時計は変えられる前提です。次の場合は不正として扱います（CI は使い捨てなので、前回見た時刻の保存には頼りません）。
  - 時計が **このリリースの日付（`BUILD_FLOOR`）より前**（1時間の許容誤差あり）＝巻き戻し
  - 時計が **キーの `iat` より前**（同じく1時間の許容誤差）＝巻き戻し、または発行側の時計の誤り
  - `nbf` より前＝まだ有効でない
- **失効：** 各リリースに、失効した `lid` の一覧（`REVOKED_LIDS`）と使えなくした署名鍵の一覧（`DISABLED_KIDS`）を埋め込みます。
- キーの読み込み順（先に見つかったものを使う）：
  1. `--license-key <key>`
  2. 環境変数 `KOTOMARK_LICENSE_KEY`
  3. ファイル `~/.kotomark/license`（キー1行）
- GitHub Action では入力 `license-key` に Secret を渡します（`license-key: ${{ secrets.KOTOMARK_LICENSE_KEY }}`）。
  `run.sh` は最初に `::add-mask::` でログからマスクし、CLI へは環境変数 `KOTOMARK_LICENSE_KEY` としてだけ渡します（コマンドラインに載せない、表示しない）。
  `run.sh`（MIT）はキーを解釈しません。
- **判定の場所：** キーの検証と、その実行の上限（無料枠の行数）の判定は `licenseForRun()`（ELv2 のエンジン `dist/kotomark.mjs` の中）の1か所だけです。
  引数の処理はキーの文字列を渡すだけで、検証も判定もしません。検証に失敗したら無料枠に戻り、異常終了はしません。
- **鍵の差し替えや検証の省略はできません。** 公開鍵・失効リスト・時計を差し替えるフラグ・環境変数・ファイルはありません。
  テストは `globalThis.__KOTOMARK_TEST_HOOKS__` で自分の鍵を注入しますが、本番のビルド（`scripts/build-cli.mjs`）はこの識別子を
  コンパイル時に `undefined` に置き換えるので、配布するバンドルには経路そのものが残りません（`release:action` とテストで確認）。
- **表示：** 有効なキーがあると Markdown レポートの見出しの下に「Licensed to 〈name〉」と出ます。キーそのものは JSON・JUnit・GitHub 形式・ログ・エラーのどこにも出しません（テストで確認）。
  バンドルの先頭には ELv2 とライセンスキー機能の回避禁止を書いたライセンス文があります。
- 状態の確認：`kotomark license status`（キーの有無と読み込み元、有効・期限切れ・不正、契約者、プラン、席数、期限、「preview: all features free」）。

| 状態 | プレビュー中（今） | プレビュー終了後 |
|---|---|---|
| キーなし | 全機能。表示なし | 無料枠 |
| 有効 | 全機能。レポートに「Licensed to」 | 有料（上限なし） |
| 期限切れ | 警告1行、全機能 | 警告1行、無料枠 |
| 不正（署名不一致・形式不正・失効・時計の巻き戻しなど） | 警告「invalid license key (理由)」、全機能 | 警告、無料枠 |

### プレビュー終了後の線引き（準備のみ・未適用）

- 無料枠でも**すべての検査**（用語・名前・敬称・プレースホルダー・タグなど）、すべての入力形式・出力形式（`--format junit/github` を含む）が使えます。
- 有料キーが必要になるのは **1回の実行で 20,000 行を超える場合**だけです（`FREE_ROWS_PER_RUN`）。超えると終了コード 2 と、入力を分けるかキーを設定するよう案内を出します。
  リポジトリが公開か非公開かの判定はしません（しきい値だけの単純な規則）。
- ホスト型 MCP は従来どおりサーバーのトークン（`src/server/auth.ts` の Solo / Studio）で管理し、このキーとは別です。
- 判定は `gateRun(rows, status, preview)` の数行だけで、テストでは `preview` を引数で切り替えています（グローバルな書き換えはしない）。
- **ブラウザ版デモ（`web/`、`site/demo/`）は、プレビュー終了後も無料で、行数の上限もキーの検査もありません**（リーダー決定、2026-10-09。
  Atlas 再レビュー F-05 への回答）。デモは利用者のブラウザの中だけで動き（サーバーへの送信なし）、試用と宣伝の入口だからです。
  ライセンスキーは CLI・GitHub Action（とホスト型 MCP のプラン）にだけ適用します。デモで大きな実行ができることは仕様で、回避とは扱いません。

## キーの発行（オーナーのみ）

発行ツールは `scripts/license-issue.mjs` です。CLI・Action のバンドルには入りません（どこからも import しない。`release:action` がバンドルに秘密鍵や発行コードがないことを確認します）。
将来は別の非公開リポジトリに移します（レビュー §5.1。公開リポジトリへの移行時に）。

1. **鍵ペアを作る（最初の1回、ローテーション時）**

   ```sh
   node scripts/license-issue.mjs --init            # 既定 ~/.kotomark/license-signing-key.pem（権限 0600）
   node scripts/license-issue.mjs --init --key /path/outside/repo/key.pem
   ```

   - 秘密鍵はリポジトリの外にだけ書けます（リポジトリ内のパスは拒否、既存ファイルは `--force` なしでは上書きしない）。
   - 標準出力に公開鍵の1行（`"k-xxxxxxxxxxxx": { key: \`-----BEGIN PUBLIC KEY-----…\`, from: "YYYY-MM-DD" },`）が出るので、
     `src/cli/license-pubkey.ts` の `LICENSE_PUBLIC_KEYS` に貼り、`npm run build:action` で再ビルドしてリリースします。
   - あとで公開鍵をもう一度表示するには `--pubkey`。

2. **キーを発行する**

   ```sh
   node scripts/license-issue.mjs --sub cust_0001 --name "Example Games 合同会社" --seats 5 --days 395 --plan studio
   # 任意：--nbf YYYY-MM-DD（有効開始日）、--features large-runs、--key <秘密鍵のパス>、--json（ペイロードを表示）
   ```

   標準出力の `KM1.…` が顧客に渡すキーです。`--days` は 400 まで、未知の `--features` は拒否します。
   発行記録（`lid`、`sub`、契約者名、席数、期限）は台帳に残してください。

## 有効期限と失効

- オフライン検証なので、発行済みのキーを**即時に失効させることはできません**。代わりに有効期限を短めにし、各リリースに失効リストを入れます。
- 推奨：年払いは **13か月（約395日）**、月払いは **2か月（約62日）** で発行し、更新のたびに新しいキーを渡します（1か月の猶予つき）。
  上限は `exp − iat ≤ 400日`（検証側でも拒否）。将来は 90日の自動更新も検討します（レビュー §5.5）。
- 個別のキーを止めるときは、その `lid` を `REVOKED_LIDS` に足してリリースします（古いバンドルでは期限まで通ります）。
- 期限切れのキーは警告だけで、プレビュー中は何も止めません。プレビュー終了後は無料枠に戻ります（無料枠の検査はすべて使える）。

## 鍵のローテーション

`kid` があるので、複数の公開鍵を同時に埋め込めます。各鍵には、その鍵で署名してよい期間（`from`、引退後は `until`）を書きます。

1. `--init --key <新しいパス>` で新しい鍵ペアを作り、出力された行を `LICENSE_PUBLIC_KEYS` に**追加**する（古い行には `until` を書く）。
2. 新しいバンドルをリリースし、以後の発行は新しい鍵で行う。
3. 古い鍵で署名したキーがすべて期限切れになったら（最長 13か月後）、古い公開鍵を削除してリリースする。
4. **秘密鍵が漏れた疑いがあるとき**は、すぐにその `kid` を `DISABLED_KIDS` に入れ（または公開鍵を削除し）、1〜2 を行ってリリースし、影響する顧客にキーを再発行する。

## リリースのたびに

- `BUILD_FLOOR`（`src/cli/license-pubkey.ts`）をリリース日に更新する（時計の巻き戻しの検出に使う。180日より古いと `release:action` が警告）。
- 失効した `lid`・無効にした `kid` を一覧に反映する。

## セキュリティ上の注意

- **秘密鍵をリポジトリ・CI・クラウドの共有ストレージに置かないでください。** `skillforge/.gitignore`、**モノレポのルートの `.gitignore`**、`.dockerignore` に `*.pem`、`*signing-key*` を入れてあります。
  `scripts/license-issue.mjs` は、git リポジトリの中（先祖に `.git` があるディレクトリ。モノレポのルートを含む）とシンボリックリンクへの書き込みを拒否します（Atlas 再レビュー F-01）。
  公開用フォルダの検査（`release:action`、`scripts/release-guard.mjs`）は、`scripts/license-issue.mjs` そのもの・鍵ペアの生成や署名のコード・PEM の秘密鍵・外装なしの秘密鍵（PKCS#8 の base64／hex、JWK の `d`）・鍵らしいファイル名・発行済みキーの形（`KM1.…`）を禁止します（`test/release-guard.test.ts`）。
- 秘密鍵は**オフラインでバックアップ**してください（暗号化した USB メモリを2つ、別の場所に保管するなど）。失うと同じ `kid` のキーを発行できなくなり、ローテーションが必要になります。
- テストは実行のたびに鍵ペアを生成して注入します。リポジトリには秘密鍵も、テスト用の固定鍵もありません。
- レビュー §5.8 の偽造パターン（署名の付け替え、ペイロードの書き換え、未知の kid、別の秘密鍵、別用途の署名、`alg:none`、公開鍵を HMAC の鍵に使う、
  期限切れ・`nbf`・`iat` が未来・時計の巻き戻し、署名長、正規でない base64url、重複キー、大きすぎるキー、未知の features、版の違い、失効した lid・無効な kid、
  本番ビルドでの鍵の差し替え）は `test/license.test.ts` にあります。
- JS を書き換えれば検証を外せますが、ELv2 はライセンスキー機能の回避を禁止しています（バンドル先頭のライセンス文、レポートの「Licensed to」、キーに顧客名と `sub` を入れて流出元を追えるようにする）。
  B2B では「正直な順守」を前提にし、それ以上の難読化はしません。
- キーの値はログに出しません（CLI の警告にも含めない。Action ではマスク）。

## PREVIEW を切り替えるとき

`PREVIEW = false` にするのは、**有料プランの販売を開始するとき**だけです。これはオーナーの判断で、事前告知（USAGE-TERMS の「Preview period」）が必要です。

- [ ] 本番の公開鍵が `LICENSE_PUBLIC_KEYS` に入っている（空のままだとすべてのキーが「invalid license key (bad signature)」になる）
- [ ] `BUILD_FLOOR` がリリース日になっている
- [ ] 価格・USAGE-TERMS・商用契約の文面が確定し、弁護士の確認が済んでいる
- [ ] `test/license.test.ts` の「preview switch is on」テストを更新する
- [ ] README・Action README・LP の「プレビュー中は無料」の表記を更新する
