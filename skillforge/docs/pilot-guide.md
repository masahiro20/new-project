# Kotomark（仮称）試用のお願い：協力者向け説明書（草案）

> 本部向けのメモは最後の「付録：運営側の手順」にあります。協力者に渡すのは「1」〜「7」です。

## 1. お願いしたいこと（所要時間：60〜90分）

日英（または英日）のゲーム台本で、**台本全体の一貫性チェック**を試し、出てきた指摘が**当たりか外れか**に印を付けてください。
私たちが知りたいのは次の2つです。

1. **誤検出がどのくらい出るか**（指摘のうち、実際には問題ではないものの割合）
2. **見逃しがどのくらいあるか**（人のチェックで見つかった問題のうち、ツールが拾えなかったものの割合）

結果は、検査の精度を上げることと、製品として出すかどうかの判断に使います。

## 2. データの扱い（先にお読みください）

- **台本は当社のサーバーに保存されません。** 検査はメモリ上で行い、終われば消えます。ログにも本文は残りません（詳細：`data-policy.md`）。
- 用語集は、あなたが「保存」を選んだときだけ、暗号化して保存します。いつでも削除できます。
- **NDA の範囲内でお使いください。** 外部に出せない台本は、次のどちらかでお願いします。
  - **ローカル版（推奨）：** あなたのパソコンだけで動き、通信しません（手順は 4-A）。
  - 固有名詞を置き換えた抜粋
- あなたが送ってくださるのは**印を付けた結果の表（labels.csv）だけ**です。この表には各行の原文と訳文が入っているので、送る前に原文・訳文の列を消すか、伏せ字にしても構いません（集計には不要です）。

## 3. 用意するもの

- 文字列テーブル：CSV / TSV / JSON / XLIFF（1.2 か 2.0）。1,000〜20,000行くらいが目安です。
  - CSV の場合、1行目に列名が必要です（例：`id,speaker,ja,en`）。`名前`／`話者` 列があると、口調と敬称の検査が効きます。
- 用語集（あれば）：JSON か CSV。**無くても試せます。** 下書きを自動で作れます（5章）。
- **人のチェックで見つかった問題の一覧（あれば、とても助かります）：** 過去のLQAのバグ票など。見逃しの測定に使います（6章）。
- Node.js 20 以上（ローカル版の場合）、または Claude Code（プラグイン版の場合）。

## 4. 実行する

### 4-A. ローカル版（通信なし）

```bash
cd skillforge
npm install
# 1) 検査してレポートを見る
npx tsx src/cli/index.ts check 台本.csv --glossary 用語集.json --out report.md
# 2) 印を付ける表を書き出す
npx tsx src/cli/index.ts labels 台本.csv --glossary 用語集.json --out labels.csv
```

### 4-B. Claude Code のプラグイン版

当社から試用トークンとサーバーのURLをお送りします。

```bash
export KOTOMARK_MCP_URL=<お送りするURL>
export KOTOMARK_TOKEN=<お送りするトークン>
claude --plugin-dir ./plugin
```

Claude Code の中で `/lqa-check 台本.csv --glossary 用語集.json` と打つと、検査とレポート作成まで進みます。
**口調の判断**（レビュー用パケット）はあなたの Claude が行います。その判断にも印を付けていただけると助かります（7章）。

### 4-C. ブラウザだけで参加する方法（インストール不要）

Node.js やコマンドを使わず、ブラウザのデモページだけで「検査 → 印付け → 送付」まで済ませられます。台本はブラウザの中だけで処理され、どこにもアップロードされません。

1. 当社からお送りする**デモのリンク**を開きます。
2. 自分の台本（または固有名詞を置き換えた抜粋）をファイルで追加するか貼り付け、用語集があれば読み込んで「チェック実行」を押します。
3. 結果の見出しの右にある **「試用モード（指摘に印を付ける）」** を押してオンにします（次回も覚えています）。
4. 各指摘の下で **「正しい指摘」「誤検知」「保留」** のどれかを選びます。誤検知には「コメント」から理由を一言入れてください。もう一度押すと取り消せます。
   - 印はそのブラウザにだけ保存され、同じ台本・用語集で開き直すと復元されます。台本や用語集を変えると、別の作業として最初からになります。
5. 結果の上の **「フィードバック」** 欄で、印を付けた件数と適合率（正しい指摘 ÷（正しい指摘＋誤検知））を確認できます。
6. **「ラベルをコピー（CSV）」** を押し、メールやチャットに貼り付けて送ってください（これが 6章の `labels.csv` と同じものです）。
   - **「原文・訳文の列を空にする（推奨）」** は最初からオンです。オンのままなら、台本の文章は含まれません（文字列ID・指摘メッセージは含まれます）。
7. 人のチェックで見つけた問題が指摘に出ていなければ、**「見逃しを追加」** に文字列ID（または `ファイル名:行`）・分類・メモを入れて「追加」し、**「見逃しをコピー（CSV）」** で同じように送ってください（6章の `known.csv` と同じ形式です）。

> 運営側へ：デモのリンクは、所有者が**先に公開（共有）設定にしてから**協力者に渡してください。非公開のままだと協力者は開けません。受け取ったテキストは `labels.csv` / `known.csv` として保存し、付録 B の `score` でそのまま集計できます。

## 5. 用語集が無い場合

```bash
npx tsx src/cli/index.ts draft 台本.csv --out 用語集-下書き.json
```

- 台本の中で繰り返し出てくる語と、その訳され方から、用語集の下書きを作ります。キャラ名は話者の列から推測します。
- **下書きは必ず目で確認してください。** 間違った訳語が入っていると、検査結果も間違います。
- 下書きを直したら、それを `--glossary` に指定して検査してください。
- **下書きをどれくらい直したかも、記録しておいてください**（例：「60語のうち12語を修正、8語を削除」）。

## 6. 印の付け方（labels.csv）

`labels.csv` をスプレッドシートで開き、`verdict` 列に次のどれかを入れてください。

| 入れる値 | 意味 |
|---|---|
| `TP`（または `正`） | 当たり。直すべき問題です |
| `FP`（または `誤`） | 外れ。問題ではありません（意図的な表現、ツールの読み違いなど） |
| `?` | 判断がつかない |
| 空欄 | 見ていない（集計から外れます） |

- `note` 列に、外れの理由を一言書いていただけると、改善に直結します（例：「回想シーンなので呼び方が違うのは意図的」「Main は名前ではない」）。
- 指摘が多すぎる場合は、**カテゴリごとに最大30件**まで見ていただければ十分です。
- **「重大度 info」は参考情報です。** 外れが多くても気にせず、そのまま印を付けてください。

### 見逃しの記録（できれば）

人のチェックで見つかった問題を、`known.csv` という名前で次の形式にまとめてください。

```csv
string_id,category,memo
ch1_005,term,魔導石の訳が Magic Stone
ch3_120,honorific,様の訳し方が他と違う
```

`category` は次のどれかです：`term`（用語）、`notation`（表記揺れ）、`name`（キャラ名）、`honorific`（敬称）、`voice`（口調）、`placeholder`、`tag`、`ruby`、`length`。

## 7. 送っていただくもの

1. `labels.csv`（印を付けたもの。原文・訳文の列は消して構いません）。ブラウザ版（4-C）ではコピーしたテキストを貼り付けて送ってください
2. `known.csv`（あれば。ブラウザ版では「見逃しをコピー（CSV）」の内容）
3. 次の5つの質問への短い回答
   1. 一番役に立った指摘は何でしたか？
   2. 一番うるさかった（無駄だった）指摘は何でしたか？
   3. 今のQAの手順のどこで使いたいですか？（翻訳中／納品前／LQAの前／使わない）
   4. 月 $29（個人）か、1タイトル $49 なら、払いますか？ 払わない場合、いくらなら払いますか？
   5. 用語集の下書きは役に立ちましたか？（何語中、何語を直しましたか）

ご協力、ありがとうございます。

## 付録：運営側の手順（本部・Forge 用）

### A. 協力者の準備

1. 協力者ごとにトークンを発行する（プラグイン版の場合）。
   ```bash
   KOTOMARK_DATA_DIR=/srv/kotomark npx tsx src/server/admin.ts token create pilot-01 --plan studio --label "pilot: 〇〇さん"
   ```
   - 表示されたトークンは1回しか出ません。安全な経路で渡します。
   - 試用が終わったら `token revoke pilot-01` で失効させ、`delete_glossary all` 相当で用語集も消します。
2. ローカル版の場合は、`skillforge/` 一式を渡す（公開リポジトリには置かない）。

### B. 集計

```bash
npx tsx src/cli/index.ts score labels.csv --known known.csv --out score.md
```

- 出力内容：
  - **カテゴリ別・ルール別の適合率**（precision = TP / (TP + FP)）
  - 全体の適合率
  - `known.csv` があれば**再現率**（recall = ツールが拾えた既知の問題 / 既知の問題）と、見逃した一覧
- 「?」と空欄は適合率の計算から外す（件数は別に出る）。
- 見逃しの照合は「同じ文字列IDに、同じカテゴリの指摘があるか」で判定する。行番号のずれには影響されない。

### C. 合格の目安（ステージ2 → 3 の判断材料）

| 指標 | 目標 | 見る理由 |
|---|---|---|
| 中核カテゴリ（term / name / honorific）の適合率 | **80%以上** | 外れが多いと使われなくなる |
| voice（口調）の適合率（warning のみ） | 60%以上 | ルールでの判定は難しい。足りない分はパケットでの判断で補う |
| 既知の問題の再現率（中核カテゴリ） | 50%以上 | 人のチェックの補助として意味があるか |
| 用語集の下書きの修正率 | 30%以下 | 下書きが「直すより作り直したほうが早い」状態でないか |
| 5人中「払う」と答えた人 | 2人以上 | ステージ3（課金）に進む材料 |

### D. 集計後にやること

1. ルール別で適合率が50%未満のものは、既定で info に下げるか、条件を絞る。
2. 外れの `note` を分類し、上位3つの原因を潰す（回帰テストを追加する）。
3. 見逃しの一覧から、ルールで拾えるものと、パケットでの判断に回すべきものを分ける。
4. 結果を `docs/pilot-results-YYYY-MM-DD.md` にまとめ、本部に報告する。
