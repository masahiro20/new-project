# 合成ベンチマーク：日→英のゲーム台本（再現率の測定）

Kotomark の本来の用途は、日本語の台本を英訳したゲームのセリフ（話者、キャラ名、敬称、口調）です。この用途で使える公開データは見つかりませんでした（`eval/misskey/source.md` の「探索の記録」）。そこで、架空の台本に既知の誤りを埋め込み、**どれだけ拾えるか（再現率）** と **余計な指摘がどれだけ出るか（精度）** を測りました。

> **合成データは実データではありません。** 結果は「ルールが想定どおり動くか」の確認であり、実際の台本での精度や再現率の保証ではありません。下の「限界」を必ず読んでください。

## ファイル

| ファイル | 内容 |
|---|---|
| `script_clean.csv` | 誤りのない台本。212 行。すべて書き下ろしで、既存作品の文章は含みません。剣と魔法の RPG で、話者6人、ナレーション、選択肢、システム文、アイテム名・説明があります。 |
| `glossary.json` | 用語 15 語（漢字の用語、カタカナの用語 5 語）、キャラクター 6 人（一人称・丁寧さ・短縮形・使わない語のプロフィール）、`honorificPolicy: "localize"` |
| `inject.mjs` | 誤りを埋め込むスクリプト（シード付きで決定的。依存なし）。`script_drifted.csv` と `truth.csv` を出力 |
| `script_drifted.csv` | 誤りを 62 件埋め込んだ台本。行の順序と行番号は clean と同じ |
| `truth.csv` | 正解データ。行、ID、カテゴリ、サブタイプ、どの列を変えたか、説明、正解とみなすルール（`expect`）、作者が事前に予想した見逃し（`predicted_gap`） |
| `score.mjs` | 採点スクリプト。Kotomark の JSON 出力と truth.csv を突き合わせる |
| `results.json` | 採点結果。設定 G（用語集あり）と A（用語集なし）について、カテゴリ別の再現率、ルール別の精度、正解に当たらない指摘とその判定 |

## 方法

1. **clean の確認**：`script_clean.csv` を用語集あり／なしで検査し、指摘が **0件** になることを確認しました。clean で何か出た場合は、書き間違いとして台本の方を直すつもりでした。結果は最初から 0件で、修正はありませんでした。
2. **埋め込み**：`node eval/synthetic-jaen/inject.mjs`（シード 20261009）。13 カテゴリ、62 件です。1 行につき 1 件だけ埋め込みます。操作はどれも単純な文字列の置換で、乱数で決めるのは「どの候補行に入れるか」だけです。スクリプトは Kotomark のエンジンを読み込みません。
3. **検査**：`script_drifted.csv` を設定 G（`glossary.json`）と設定 A（`--no-glossary`）で検査しました。
4. **採点**：`score.mjs` で採点しました。正解行に、`expect` に挙げたルールの指摘があれば「発見」としています。重大度は問いません。警告以上に限った数も併記しています（`foundCi`）。正解行以外の指摘は、評価者が手で判定しました（`score.mjs` の `JUDGEMENTS`）。判定のない指摘は `unjudged` として残り、精度の計算には入りません。

```bash
cd skillforge
node eval/synthetic-jaen/inject.mjs                       # → script_drifted.csv, truth.csv
S=/tmp/synth; mkdir -p $S; D=eval/synthetic-jaen
for f in clean drifted; do
  npx tsx src/cli/index.ts check $D/script_$f.csv --glossary $D/glossary.json --format json --fail-on never > $S/$f.G.json
  npx tsx src/cli/index.ts check $D/script_$f.csv --no-glossary          --format json --fail-on never > $S/$f.A.json
done
node $D/score.mjs --truth $D/truth.csv --clean-G $S/clean.G.json --drifted-G $S/drifted.G.json \
  --clean-A $S/clean.A.json --drifted-A $S/drifted.A.json --out $D/results.json
```

エンジンの状態は、2026-10-09 時点の skillforge 作業ツリーです（この評価で src/ は変更していません）。

## 結果（2026-10-09）

**誤検知は1件**：`script_drifted.csv:82` の `honorific.drift`（clean のままの「Sir Gald」）。ハヤテの「ガルド殿」の英訳が、Sir Gald / Gald-dono / Gald の 1対1対1 の同数になりました。エンジンは同数のときも先頭を「多数派」とみなし、しかも方針違反の `Gald-dono` を基準に選んで、正しい行を指摘しています。同じ理由で 155 行目（本物の揺れ）への助言も「Gald-dono に合わせる」になっており、検出はしても修正案が誤っています。

### 設定 A（用語集なし）：再現率 21/62 = 0.34（警告以上では 18/62）、精度 23/23 = 1.00

用語・キャラ名・敬称・口調は、用語集とプロフィールがないと出ません（設計どおり）。一人称は多数決で 3件出ますが、情報レベルです。用語集なしで拾えるのは、カタカナ表記・プレースホルダー・タグ・ルビ・文字数です。**日→英の台本で価値を出すには、キャラ設定（プロフィール）の入力が前提**になります。

## 見逃しの上位3つと修正案

1. **話者ラベルの正規化（2/5 見逃し）**：`src/core/checks/names.ts`
   - `findCharacter` と `normSpeaker` で、括弧書きの肩書き（`ガルド（騎士長）`、`Gald (armored)`）を外してからキャラに解決する。そのうえで、`name.speaker-label`（表記が多数派と違う）として報告する。
   - ひらがなをカタカナに寄せる（`りん` → `リン`）。`normSpeaker` の `katakanaKey` の前に、ひらがな → カタカナ変換（U+3041–3096 に +0x60）を入れる。`name.speaker-unknown` の距離計算にも同じ変換を使う。
2. **一人称の検出漏れ（2/5 見逃し）**：`src/core/checks/voice.ts`
   - `KANJI_PRONOUN` に `余`・`我`・`吾` を加える（`AFTER` があるので、余計・余裕・余り・我慢は一致しない）。プロフィールの `firstPerson` に書かれた語は、リストになくても必ず検出対象にする。今は、`余` をプロフィールに書いても一度も検出されず、黙って素通りします。
   - `KANA_PRONOUN` の直前条件（ひらがなの後は助詞の後だけ）を、連体形の語尾 `[るたいなだの]` の後でも、3モーラ以上の代名詞（わたくし・わたし・あたし）に限って許可する。「巫女である**わたくし**」「戦う**あたし**」が今は検出されません。clean 版の「であるわたくし」も検出されておらず、本来の一人称の集計からも漏れています。
3. **常体の判定が狭い（丁寧さ 1/4 見逃し）と、名前を落とした呼び方（敬称 1/7）**
   - `voice.ts` の `PLAIN_END` には、動詞の辞書形・た形・ている形（`る` `た` `ている` `ない` `う`）がありません。そのため、丁寧キャラが「〜ている。」と言っても、丁寧でも常体でもない扱いになります。プロフィールで `politeness` が指定されたキャラに限り、文末の `(る|た|ない|う)[。！？…]*$` を常体とみなす。誤検知が出やすい多数決モードには入れない。
   - `checkHonorifics`：日本語に「名前＋敬称」があるのに英語に名前がない行（"Your Highness"、"my lady"）は、今は `name.missing`（情報）としか出ません。同じ話者・相手・敬称のグループの多数派に呼び方がある場合（Lady Ceres ×4）は、`honorific.drift`（情報、「名前を落として別の呼び方になっている」）として出す。
   - あわせて精度の修正：`honorific.drift` で多数派を決めるとき、`honorificPolicy` に違反する形（`-dono` など）を候補から外す。同数のときは「多数派」と断定せず、全員に「呼び方が揃っていない」とだけ出す（上記の 82 行目の誤検知と、155 行目の誤った助言の原因）。

ほか：3文字の名前（Mio→Mia、Rin→Ran）は、`name.near-miss` の長さ条件（4文字以上）で対象外です。同じ行の日本語にそのキャラ名がある場合に限り、距離1を警告にする案があります（`names.ts`）。

## 限界（必ず併記すること）

- **合成データは実データではありません。** 文はどれも短く、表現の幅も狭いです。実際の台本にある長い独白、方言、話者のいない地の文の多さ、複数行のセル、同じキャラの意図的な口調の変化（怒ったときに敬語が崩れる、など）は、ほとんど含みません。
- **作者のバイアス**：評価者は、台本と埋め込み処理を書く**前に**エンジンのソース（`checks/*.ts`、`text.ts`）を読んでいます。そのため、
  - clean の台本は、エンジンが誤検知しにくい書き方に寄っています。たとえば、ガルドの台詞に「ます」を含む動詞（覚ます）を入れない、「黙っておれ」を避ける、などです。clean で 0件という結果は、実データでの精度を意味しません。
  - 埋め込む誤りも、ルールで捉えられる形が多くなっています。予想した見逃しは `truth.csv` の `predicted_gap` に記録しました。予想は 6件で、そのうち 5件は実際に見逃し、1件（Mia）は情報レベルで検出されました。予想外の見逃しは1件（「であるわたし」）でした。
  - 再現率 0.90 は、**ルールの実装が仕様どおりかの確認**として読んでください。「台本の問題の 90% を拾う」という主張には使えません。
- 誤りは 1 行に 1 件だけです。1 行に複数の誤りがある場合や、誤りが多数派になる場合（揺れの方が多い）は試していません。
- 日本語の原文側の誤り（一人称・丁寧さ・カタカナ・敬称の変更）は、日→英の案件では**原文の担当者に返す種類の指摘**です。翻訳者の誤りではありません。英語側の口調の揺れ（タメ口になった、など）は、ルールでは短縮形と禁止語しか見ていません。それ以外は、レビュー用パケット（利用者側の AI が判断）の役割で、このベンチマークでは測っていません。
- 判定は評価者1人です（正解行以外の指摘は1件だけでした）。
